# SteamGames-Monitor

[简体中文](README.md) | [繁體中文](README.zh-TW.md) | [English](README.en.md) | [Deutsch](README.de.md) | [Français](README.fr.md) | [Italiano](README.it.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [조선어](README.ko-KP.md) | [Nederlands](README.nl.md) | [Русский](README.ru.md)

Интерфейс доступен на упрощённом китайском, традиционном китайском, английском, немецком, французском, итальянском, японском, корейском, северокорейском, нидерландском и русском языках. Переключайте его в правом верхнем углу; эта настройка не зависит от языка контента Steam.

Самостоятельно размещаемая многопользовательская система мониторинга статуса продаж игр и DLC в Steam. Данные хранятся в SQLite; система отслеживает **скорое прекращение продаж / снятие с продажи, скидки и релизы** и отправляет уведомления через групповые боты WeCom, боты Feishu, боты DingTalk или SMTP-почту.
Один и тот же процесс одновременно предоставляет веб-интерфейс, REST API, планировщик опроса Steam, очередь доставки уведомлений, колбэки Feishu / Lark / DingTalk, а также постоянные соединения Feishu, DingTalk Stream и WeCom, что подходит для развёртывания на одном хосте через Docker Compose.

## Возможности

- **Независимые учётные записи нескольких пользователей**: учётные записи создаёт администратор, у каждого пользователя свои объекты мониторинга, события, каналы уведомлений и боты команд; данные строго изолированы.
- **Объекты мониторинга**: поддерживаются appid, ссылка на магазин и поиск по названию; возможен массовый импорт всех DLC базовой игры.
- **Изменения статуса**: релиз (переключение coming soon), подтверждение / изменение даты выхода, начало / изменение / окончание распродажи, изменение базовой цены, недоступность (снятие с продажи) и восстановление.
- **Определение снятия с продажи**: факт снятия подтверждается только после двух последовательных изменений статуса доступности в магазине; дополнительно используется раннее предупреждение по ключевым словам в новостях Steam (эвристика, только для справки).
- **Каналы уведомлений**: групповой бот WeCom, пользовательский бот Feishu, пользовательский бот DingTalk, пользовательский WebHook, SMTP-почта; при неудаче выполняется автоматическая повторная попытка.
- **Боты команд**: приложение-бот Feishu / Lark (создание одним сканированием QR-кода, HTTP-колбэк или постоянное WebSocket-соединение), бот DingTalk (создание одним сканированием QR-кода, HTTP-колбэк или постоянное соединение Stream), постоянное соединение интеллектуального бота WeCom; поддерживаются создание по QR-коду, веб-авторизация неавторизованных пользователей и уведомления о событиях; доступны команды `/add`, `/list`, `/price`, `/check`, `/pause`, `/resume`, `/remove`, `/adddlc`, `/events`, `/cancel`; WeChat ClawBot и QQ Bot подключаются по официальным протоколам платформ.
- **Удобство эксплуатации**: проверка работоспособности, образы Docker, резервное копирование базы данных на ходу, настраиваемая политика хранения данных.

## Технологический стек

- Node.js 24 + TypeScript (ESM), Hono, `node:sqlite` (WAL), Zod, Nodemailer
- Vue 3 + Vite + Pinia + Vue Router (собранный фронтенд отдаётся напрямую процессом Node)
- Тестирование: Vitest (модульные тесты), Playwright (end-to-end)

## Быстрый старт (локальная разработка)

Требуются Node.js `^22.18 || >=24.12` и pnpm.

```bash
pnpm install
cp .env.example .env
# Отредактируйте .env: заполните как минимум APP_SECRET (не менее 32 символов)
openssl rand -base64 48
pnpm dev
```

- Веб-интерфейс: http://localhost:5173
- Серверный API: http://localhost:8787

При первом запуске просто откройте веб-интерфейс, создайте первую учётную запись администратора и выберите регион, язык и часовой пояс. **У региона нет значения по умолчанию**; учётная запись, не завершившая инициализацию, не может добавлять объекты мониторинга. Интерфейс инициализации автоматически перестаёт работать после создания первого администратора; поскольку токен инициализации больше не требуется, не выставляйте экземпляр в интернет до завершения инициализации — сразу после развёртывания выполните инициализацию.

### Сборка для production

```bash
pnpm build   # проверка типов + сборка фронтенда dist/ + серверного dist-server/index.js
pnpm start   # требуется предварительная сборка; Node одновременно отдаёт API и статический фронтенд
```

## Переменные окружения

| Переменная | Описание |
| --- | --- |
| `NODE_ENV` | При значении `production` принудительно проверяется `APP_SECRET` |
| `HOST` / `PORT` | Адрес и порт прослушивания, по умолчанию `0.0.0.0:8787` |
| `DATA_DIR` | Каталог данных, по умолчанию `./data` (в Docker — `/data`) |
| `DATABASE_PATH` | Путь к файлу SQLite, по умолчанию `${DATA_DIR}/steam-monitor.db` |
| `APP_SECRET` | Обязательно, ≥32 символов. Используется для производного ключа шифрования учётных данных каналов и ботов; **после потери сохранённые ключи расшифровать невозможно** |
| `PUBLIC_BASE_URL` | Внешний адрес доступа; используется для формирования адресов колбэков Feishu / Lark / DingTalk, ссылок веб-авторизации WeCom и проверки CSRF; для постоянного соединения публичный колбэк не нужен |
| `TRUSTED_ORIGINS` | Дополнительные разрешённые Origin через запятую (в разработке — с `http://localhost:5173`) |
| `COOKIE_SECURE` | При развёртывании по HTTPS установите `1` |
| `TRUST_PROXY` | Количество уровней обратного прокси |
| `MAX_TOTAL_MONITORS` | Глобальный лимит объектов мониторинга, по умолчанию 2000 |
| `ALLOW_INSECURE_WEBHOOKS` | Устанавливайте `1` только для тестов: разрешает http-адреса и Webhook во внутренней сети |
| `ENABLE_DEV_COMMANDS` / `DEV_COMMAND_TOKEN` | Для разработки: `/api/dev/command` для имитации команд |
| `LOG_LEVEL` | `debug` / `info` / `warn` / `error`; файловые логи пишутся в `${DATA_DIR}/logs/app-YYYY-MM-DD.log` |
| `STEAM_STORE_BASE_URL` / `STEAM_API_BASE_URL` | Необязательно, переопределяют конечные точки Steam (для тестов / прокси) |

В среде с прокси можно использовать `HTTPS_PROXY`, `NODE_USE_ENV_PROXY=1` и `NO_PROXY`. Если Node не распознаёт системную цепочку сертификатов, при запуске сервис объединяет системные CA (`lib/tls.ts`).

## Развёртывание через Docker Compose

GitHub Actions публикует образ-снимок (`dev`) при пуше в ветку `main`, а при пуше тега стабильной версии (например, `v1.1.1`) — семантическую версию и переводит `latest` на эту стабильную версию:

```bash
# последняя стабильная версия
docker pull akarinliu2000/steamgames-monitor:latest
# текущая стабильная версия 1.1.1
docker pull akarinliu2000/steamgames-monitor:1.1.1
# последний снимок ветки main
docker pull akarinliu2000/steamgames-monitor:dev
```

Образ поддерживает `linux/amd64` и `linux/arm64`; Docker автоматически выбирает его по архитектуре хоста. Доступны два базовых образа:

| Тег | Базовый образ | Описание |
| --- | --- | --- |
| `latest` / `1.1.1` / `1.1` | Debian slim (`node:24-bookworm-slim`) | Последняя стабильная версия |
| `latest-alpine` / `1.1.1-alpine` / `1.1-alpine` | Alpine (`node:24-alpine`) | Последняя стабильная версия Alpine |
| `dev` | Debian slim | Последний снимок ветки `main` |
| `dev-alpine` | Alpine | Последний Alpine-снимок ветки `main` |

`latest` перемещается только на тегах без предварительного выпуска (например, `v1.1.1`); теги с `-rc` / `-beta` не перезаписывают `latest`. Обычные коммиты в ветку `main` обновляют только теги `dev` / `dev-alpine` и `sha-*`.

```bash
docker pull akarinliu2000/steamgames-monitor:latest-alpine
# локальная сборка версии Alpine
docker build --build-arg BASE_IMAGE=node:24-alpine -t steam-monitor:alpine .
```

Запуск напрямую из образа:

```bash
cp .env.example .env
# укажите APP_SECRET, PUBLIC_BASE_URL (публичный HTTPS-адрес), COOKIE_SECURE=1, TRUST_PROXY=1
docker run -d --name steam-monitor \
  --env-file .env \
  -p 8787:8787 \
  -v "$(pwd)/data:/data" \
  --restart unless-stopped \
  akarinliu2000/steamgames-monitor:latest
```

Просмотр логов контейнера:

```bash
# способ docker run
docker logs -f steam-monitor

# способ docker compose
docker compose logs -f steam-monitor
```

Если `docker ps` показывает случайное имя контейнера (например, `nervous_roentgen`), значит, при запуске не был указан `--name steam-monitor`; в этом случае `docker compose logs` не покажет этот контейнер, используйте `docker logs -f <фактическое имя контейнера>`. При отдельном `docker run` конфигурация, такая как `LOG_LEVEL` и `PUBLIC_BASE_URL`, загружается только при передаче `--env-file .env`; без неё уровень логирования по умолчанию — `info`, а `PUBLIC_BASE_URL` — `http://localhost:8787`.

Логи приложения также записываются по дате UTC в `${DATA_DIR}/logs/app-YYYY-MM-DD.log`; в Docker они по умолчанию монтируются в каталог хоста `./data/logs/`. Stdout контейнера сохраняется, его можно просматривать через `docker logs`. Файлы логов не удаляются автоматически — архивируйте или очищайте их по мере необходимости.

Запуск Compose с образом из Docker Hub:

```bash
docker compose pull
docker compose up -d
```

Локальная пересборка после изменения кода (перезаписывает локальный образ одноимённым тегом Docker Hub):

```bash
docker compose up -d --build
```

### Публикация в Docker Hub

Адрес Docker Hub: <https://hub.docker.com/r/akarinliu2000/steamgames-monitor> (`akarinliu2000/steamgames-monitor`)

Файл `.github/workflows/dockerhub.yml` публикует снимок `dev` при пуше в ветку `main`, а при пуше тега стабильной версии — семантическую версию и обновляет `latest`:

- В Secrets репозитория необходимо настроить `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN` (Docker Hub Access Token с правами Read & Write).
- Текущие образы: `docker.io/akarinliu2000/steamgames-monitor:latest`, `:1.1.1`, `:dev` (Debian), а также соответствующие версии `-alpine`; все они мультиархитектурные amd64/arm64.
- Репозиторий Docker Hub является публичным, образ можно загружать анонимно.
- Если требуется пространство имён организации, добавьте переменную репозитория `DOCKERHUB_REPOSITORY` (например, `myorg/steamgames-monitor`).

```bash
docker pull akarinliu2000/steamgames-monitor:latest
```

```bash
gh secret set DOCKERHUB_USERNAME --repo AkarinLiu/SteamGames-Monitor
gh secret set DOCKERHUB_TOKEN --repo AkarinLiu/SteamGames-Monitor
```

- Данные сохраняются на хосте в `./data` (этот каталог монтируется в контейнер как `/data`); туда записываются база данных, резервные копии и логи `logs/`.
- Точка входа образа исправляет права на `./data`, затем понижает привилегии до пользователя `node` внутри контейнера; в Linux можно также вручную выполнить `sudo chown -R 1000:1000 data`.
- Входной скрипт автоматически отображает относительные `DATA_DIR` / `DATABASE_PATH` из `.env` в `/data`, поэтому даже отдельный `docker run --env-file .env` корректно открывает мастер инициализации.
- В контейнере каталогом данных всегда является `/data`; Compose переопределяет `DATA_DIR` / `DATABASE_PATH` из `.env`, не заменяйте их на относительные пути внутри контейнера.
- `PUBLIC_BASE_URL` должен совпадать с фактическим адресом, по которому открывается браузер (например, `http://192.168.1.10:8787`); при использовании домена / HTTPS-прокси его также нужно изменить.
- `APP_SECRET` обязателен; без него контейнер завершится. Ошибки запуска можно посмотреть командой `docker compose logs -f steam-monitor`.
- После изменения `.env` выполните `docker compose up -d`, чтобы пересоздать контейнер и применить изменения.
- Процесс приложения работает не от root; встроенный `HEALTHCHECK` обращается к `/api/health`.
- Обновление образа: `docker compose pull && docker compose up -d`; локальная сборка: `docker compose up -d --build`; остановка: `docker compose down` (данные сохраняются).
- Обратный прокси: учтите следующее:
  - Необходимо передавать **исходное тело запроса** для `/webhooks/*` без изменений (не переписывайте и не сериализуйте заново).
  - `client_max_body_size 1m`, тайм-аут чтения ≥10 с.
  - Адреса Feishu / Lark / DingTalk с HTTP-колбэком должны быть доступны из интернета по HTTPS; при использовании исходящих постоянных соединений Feishu / Lark, DingTalk Stream и интеллектуального бота WeCom адрес колбэка не требуется.

## Настройка каналов уведомлений

Добавьте канал на странице «Каналы уведомлений»:

- **Групповой бот WeCom**: настройки группы → групповые роботы → добавить робота, скопируйте Webhook.
- **Пользовательский бот Feishu**: настройки группы → групповые роботы → пользовательский робот; если включена проверка подписи, укажите также ключ подписи.
- **Пользовательский бот DingTalk**: настройки группы → умный групповой помощник → добавить робота; если включена подпись, укажите также секрет подписи.
- **Пользовательский WebHook**: укажите произвольный HTTPS-эндпоинт; система отправляет события методом POST в формате JSON, опционально можно задать ключ подписи HMAC и заголовок Authorization.
- **SMTP**: укажите сервер, порт, SSL/TLS, отправителя и получателей (несколько адресов через запятую).

Ключи хранятся в зашифрованном виде с использованием AES-256-GCM на основе производного ключа от `APP_SECRET`; API не возвращает открытый текст, а пустое поле при редактировании означает сохранение прежнего значения.

Формат запросов, поля Payload и алгоритм подписи для пользовательского WebHook описаны в [docs/CUSTOM_WEBHOOK.ru.md](docs/CUSTOM_WEBHOOK.ru.md).

Если в разделе «Подписка на события» не отмечено ни одного события, канал получает все события, кроме «ошибки проверки».

## Подключение ботов команд

Создайте бота на странице «Боты команд»:

| Платформа | Способ подключения | Описание |
| --- | --- | --- |
| Feishu / Lark | HTTP-колбэк или постоянное WebSocket-соединение | Можно создать приложение одним сканированием QR-кода или вручную указать App ID / App Secret; для постоянного соединения на открытой платформе нужно выбрать «Получать события через постоянное соединение» и подписаться на `im.message.receive_v1` |
| DingTalk | HTTP-колбэк или постоянное соединение Stream | Можно создать бота одним сканированием QR-кода или вручную указать Client ID / Secret; для HTTP-колбэка укажите App Secret для проверки подписи, режим Stream не требует публичного адреса |
| WeCom | Постоянное WebSocket-соединение (без адреса колбэка) | Создайте интеллектуального бота в административной консоли, выберите режим API → постоянное соединение, укажите Bot ID / Secret; сервис сам подключается к `wss://openws.work.weixin.qq.com` |

Адрес HTTP-колбэка Feishu / Lark — `POST /webhooks/feishu/<slug>`; режим колбэка поддерживает Encrypt Key / Verification Token, а режим постоянного соединения не требует публичного адреса колбэка. Параметр «Версия» в конфигурации переключает Feishu (`open.feishu.cn`) и международную версию Lark (`open.larksuite.com`).

**Добавление Feishu / Lark по QR-коду (рекомендуется)**: на странице «Боты команд» нажмите **QR-код Feishu / Lark**, выберите «Feishu» или «Международная версия Lark» и отсканируйте код соответствующим клиентом, следуя подсказкам на странице для создания приложения. Система автоматически получит App ID / App Secret и сохранит `open_id` сканировавшего как идентификатор владельца; QR-код действителен 10 минут. При создании по QR-коду создаётся приложение `PersonalAgent` с уже настроенными возможностями бота и подпиской на события сообщений; после создания можно найти приложение по названию в Feishu / Lark и начать диалог или добавить его в групповой чат.

**Добавление DingTalk по QR-коду (рекомендуется)**: нажмите **Добавить DingTalk по QR-коду**, отсканируйте код мобильным DingTalk и, следуя подсказкам на странице, выберите организацию и заполните данные бота. Система автоматически получит Client ID / Client Secret, использует Client ID как Robot Code и включит постоянное соединение Stream; QR-код действителен 10 минут. После создания бота можно найти его в DingTalk и начать личный чат или добавить в групповой чат. Когда участник впервые отправляет команду, он получает ссылку на веб-авторизацию; после того как учётная запись, которой принадлежит бот, войдёт на веб-страницу и подтвердит доступ, ботом можно пользоваться.

Постоянное соединение WeCom устанавливается сервером исходящим подключением и не требует публичного IP, Token или EncodingAESKey. Для одного бота одновременно допускается только одно активное соединение; при развёртывании нескольких экземпляров они будут вытеснять друг друга. Устаревшая конфигурация колбэка собственного приложения WeCom больше не поддерживается — укажите Bot ID / Secret интеллектуального бота.

Можно также нажать **Добавить WeCom по QR-коду** и отсканировать код в WeCom с учётной записью, имеющей право создавать ботов; система автоматически получит Bot ID / Secret, создаст бота и установит постоянное соединение. QR-код действителен 5 минут. После того как участник впервые отправит команду, он получит ссылку на веб-авторизацию; её должен одобрить владелец бота, войдя на веб-страницу, либо этого пользователя можно сразу добавить в список разрешённых.

Если неавторизованный пользователь Feishu / Lark, DingTalk или WeCom отправляет команду, бот отвечает одноразовой ссылкой на веб-авторизацию и не выполняет команду. После входа на страницу по ссылке пользователь веб-интерфейса, которому принадлежит бот, может выбрать для этого пользователя платформы роль «только чтение» или «администратор» и подтвердить доступ; ссылка действительна 30 минут. `PUBLIC_BASE_URL` должен быть доступен из браузера, иначе ссылка не откроется.

На странице редактирования бота команд можно включить **Получать уведомления о событиях**: после включения события релизов, распродаж, снятия с продажи и т. п. будут доставляться в сеанс, который последним использовал авторизованный пользователь этого бота. Чтобы система запомнила цель уведомлений, авторизованный пользователь должен сначала отправить в чат хотя бы одну команду; при отсутствии последнего сеанса доставка не выполняется. Для уведомлений о событиях DingTalk также необходимо указать App Key, App Secret и Robot Code.

Команды бота всегда применяются к данным **учётной записи, которой принадлежит бот**. Все пользователи платформ (включая ID владельца, распознанный при сканировании QR-кода) должны сначала пройти веб-авторизацию или быть добавлены в список разрешённых; иначе бот возвращает только одноразовую ссылку авторизации и не выполняет команду. При подтверждении можно выбрать `viewer` (только чтение) или `admin`. ID владельца теперь используется только для идентификации. Подробные шаги см. в [docs/BOT_INTEGRATION.ru.md](docs/BOT_INTEGRATION.ru.md).

Подключение WeChat ClawBot (iLink) и QQ Bot выполняется по официальным протоколам платформ; после завершения они появятся на той же странице.

## Регион и перебазирование

Регион — настройка уровня пользователя. При изменении региона все существующие объекты мониторинга пользователя перебазируются: очищаются опорные точки распродаж, состояние сбрасывается, а первый цикл проверки только записывает снимок и не создаёт событий, чтобы избежать ложных срабатываний из-за разницы цен в регионах. На других пользователей это не влияет.

## Сброс пароля

Выполните в терминале сервера (вход в веб-интерфейс не требуется):

```bash
pnpm reset-password <имя пользователя>
pnpm reset-password <имя пользователя> --password 'new-password-123'
pnpm reset-password <имя пользователя> --enable
```

Развёртывание в Docker:

```bash
docker compose exec steam-monitor node dist-server/reset-password.js <имя пользователя>
```

- Если не указать `--password`, будет сгенерирован случайный временный пароль и выведен в терминал.
- После сброса устанавливается `must_change_password=1`, и при следующем входе пользователь обязан сменить пароль; все существующие сеансы этого пользователя становятся недействительными.
- Отключённая учётная запись по умолчанию остаётся отключённой; с флагом `--enable` её можно одновременно включить.
- Команда работает напрямую с SQLite и не зависит от `APP_SECRET`; база данных определяется через `DATA_DIR` / `DATABASE_PATH`.

## Резервное копирование и восстановление

```bash
pnpm backup
```

Скрипт с помощью `VACUUM INTO` создаёт в `${DATA_DIR}/backups/` файл `steam-monitor-YYYYMMDD-HHmm.db` и по умолчанию хранит последние 14 копий. В Docker можно выполнить:

```bash
docker compose exec steam-monitor node_modules/.bin/tsx scripts/backup.ts
```

Порядок восстановления: остановите контейнер → замените `steam-monitor.db` файлом резервной копии → удалите файлы `-wal` / `-shm` в том же каталоге → запустите контейнер. **Обязательно сохраните резервную копию `APP_SECRET` из `.env`**, иначе зашифрованные ключи каналов и ботов восстановить не удастся и их придётся вводить заново.

## Тестирование

```bash
pnpm type-check
pnpm lint
pnpm test:unit
pnpm test:e2e   # сначала установите браузер Playwright: pnpm exec playwright install chromium
```

End-to-end тесты:

1. создают новую базу данных в `data/e2e`, запускают бэкенд (4180), Vite (4181) и mock-сервис (9998);
2. используют mock-интерфейсы Steam для прогона полного цикла релиза, распродажи, снятия с продажи и восстановления;
3. проверяют уведомления WeCom, пользовательский WebHook, SMTP-почту, колбэки и конфигурацию QR-кода Feishu / Lark / DingTalk, постоянные соединения Feishu / DingTalk / WeCom и изоляцию пользователей.

`scripts/mock-receiver.ts` можно запустить отдельно для локальной отладки:

```bash
pnpm mock:receiver
# Webhook уведомлений: http://127.0.0.1:9999/<любой путь>
# SMTP sink: 127.0.0.1:1025
# Перехваченные запросы: GET http://127.0.0.1:9999/_requests
# Имитация Steam: http://127.0.0.1:9999/steam-store и /steam-api
```

Вместе с `ALLOW_INSECURE_WEBHOOKS=1` и `STEAM_STORE_BASE_URL` / `STEAM_API_BASE_URL` можно полностью отладить систему в офлайн-режиме.

## Известные ограничения

- Интерфейс магазина Steam неофициальный и может меняться или ограничивать частоту запросов; невозможно отличить «снято с продажи / недоступно в регионе / некорректный appid», поэтому система использует правило «ранее было доступно + два последовательных отказа», чтобы снизить число ложных срабатываний.
- Предупреждение по ключевым словам в новостях охватывает только новости / объявления Steam, носит эвристический характер и требует ручного подтверждения.
- Точное время окончания распродажи неизвестно; событие `sale_end` зависит от того, обнаружит ли следующий цикл опроса нулевую скидку.
- Групповой бот WeCom умеет только отправлять сообщения; для команд в группе используйте постоянное соединение интеллектуального бота WeCom. Для одного бота поддерживается только одно активное постоянное соединение; при развёртывании нескольких экземпляров они будут вытеснять друг друга.
- Подключение WeChat ClawBot (iLink) и QQ Bot выполняется по официальным протоколам платформ.
- Развёртывание в одном экземпляре, SQLite с единственным писателем; высокая доступность не обеспечивается.
- Разные регионы пользователей приводят к тому, что одна и та же игра кэшируется и запрашивается отдельно по каждому региону.

