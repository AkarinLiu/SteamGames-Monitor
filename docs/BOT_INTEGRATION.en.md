# Feishu / Lark, DingTalk, and WeCom Integration Guide

This document explains how to connect Feishu / Lark, DingTalk, and WeCom to Steam Games Monitor. The project offers two capabilities that do not replace each other, so first confirm your goal:

| Goal | What to create on the platform | Where in the system | Direction |
| ----------------------------------- | ---------------------------------------------------------------------------------------- | -------------- | ------------------------ |
| Receive notifications for releases, discounts, delistings, etc. | Group custom bot / group bot Webhook | **Notification channels** | One-way: system → group |
| Send `/add`, `/list`, and other commands in chat | Feishu / Lark enterprise custom app / DingTalk enterprise internal bot (Outgoing) / WeCom intelligent bot (long connection) | **Command bots** | Two-way: platform → system → platform |

> Group bot Webhooks can usually only send messages and cannot receive commands. Feishu / Lark and DingTalk both support one-click app creation by QR code, with a choice of HTTP callback or long connection; WeCom requires creating an intelligent bot and using a long connection.
>
> Notification channels and command bots are two independent configurations: you can configure notifications only, commands only, or both for the same platform.

## 1. General preparation

### 1.1 Public HTTPS and PUBLIC_BASE_URL (HTTP callback mode)

Feishu / Lark / DingTalk using **HTTP callbacks** require the platform to push messages to your server, so the following must be satisfied:

- The service must be reachable from the public internet over an **HTTPS** address accepted by the platform.
- `PUBLIC_BASE_URL` in `.env` must match the address browsers actually use, e.g. `https://steam.example.com`.
- Do not use the default `http://localhost:8787`, otherwise the platform cannot reach the callback URLs generated by the system.
- A dedicated domain or subdomain is recommended. Callback paths are fixed to `/webhooks/...`, so do not deploy under a subpath that requires additional rewriting.

The callback URLs shown in the system are generated by the following rules:

```text
Feishu / Lark  https://<PUBLIC_BASE_URL host>/webhooks/feishu/<slug>
DingTalk       https://<PUBLIC_BASE_URL host>/webhooks/dingtalk/<slug>
```

`<slug>` is generated randomly when the bot is created and is different for each bot. Changing `PUBLIC_BASE_URL` changes the callback URLs, so the platform console must be updated accordingly.

> Feishu / Lark **long connection mode**, DingTalk **Stream mode**, and WeCom intelligent bots all establish outbound connections initiated by the service, so they need no public callback address, public IP, Token, or EncodingAESKey. Feishu / Lark apps and DingTalk bots created by QR scanning use long connections by default.
>
> `PUBLIC_BASE_URL` must still be reachable from the browser of the bot owner: the web authorization links received by unauthorized users use that address.

### 1.2 Reverse proxy requirements

Nginx, Caddy, Traefik, or a cloud load balancer must satisfy the following (affects only Feishu / Lark / DingTalk HTTP callbacks):

- **Forward the request body unchanged**; do not re-serialize the JSON, compress, or modify the content — Feishu / Lark and DingTalk signatures are based on the raw request body.
- Preserve platform request headers: `X-Lark-Request-Timestamp`, `X-Lark-Request-Nonce`, and `X-Lark-Signature` for Feishu, and `timestamp` and `sign` for DingTalk.
- Preserve query parameters; do not drop signature parameters.
- Do not add login, Basic Auth, HTML redirects, or WAF interactive challenges to `/webhooks/*`.
- Request body limit of at least 1 MB; read timeout of at least 10 seconds.
- Use a trusted TLS certificate; the platform validates the certificate chain.

Feishu / Lark long connections, DingTalk Stream, and WeCom long connections do not pass through the reverse proxy; the server only needs outbound access to the corresponding platform (Lark uses `open.larksuite.com`, DingTalk Stream uses `api.dingtalk.com`).

### 1.3 Time synchronization and secrets

- The server must have NTP time synchronization enabled. Feishu / Lark signatures allow a ±300 second deviation, and DingTalk Outgoing callbacks allow a ±1 hour deviation.
- `APP_SECRET` (at least 32 characters) encrypts stored channel and bot credentials. **Do not change or lose it casually**: after a change, saved App Secrets, bot Secrets, Encrypt Keys, etc. cannot be decrypted and must be re-entered.
- Bot credentials are stored in SQLite encrypted with AES-256-GCM; neither the API nor the UI echoes plaintext, and leaving a field empty when editing keeps the existing value.

### 1.4 Recommended creation order

Feishu / Lark (QR scan, recommended):

1. On "Command bots", click "Feishu / Lark QR", choose Feishu or Lark international, and scan.
2. Create and confirm the app on the platform page; the system automatically stores the App ID / App Secret and the owner's `open_id`, and enables the long connection.
3. Search for the app name in Feishu / Lark to start a one-to-one chat, or add the bot to a group.
4. Send `/help` to verify the command and reply path.

Feishu / Lark (manual):

1. Create a bot in the system, choosing the version (Feishu / Lark) and the event receiving method (HTTP callback / long connection).
2. HTTP callback: copy the callback URL into the platform console and configure the Encrypt Key / Verification Token; long connection: choose "Receive events via long connection" on the platform.
3. Subscribe to `im.message.receive_v1` and request message read and send permissions.
4. Publish the app, add the bot to groups, or set the availability scope.
5. Send `/help` to verify.

DingTalk (QR scan, recommended):

1. On "Command bots", click "Add DingTalk bot by QR", scan with the DingTalk mobile app, and confirm creation.
2. The system automatically stores the Client ID / Client Secret, uses the Client ID as the Robot Code, and enables the Stream long connection.
3. Search for the bot in DingTalk to start a one-to-one chat, or add the bot to a group.
4. Send `/help` to verify.

DingTalk (manual):

1. Create a bot in the system, choose the message receiving mode, and copy the callback URL (HTTP mode).
2. Create an app / bot in the platform console and fill in the callback URL and secret, or select Stream mode in the bot configuration.
3. When saving the callback, the platform usually performs URL verification; make sure the system is running and the bot is enabled.
4. Publish the app on the platform, add the bot to groups, or set the availability scope.
5. Send `/help` to verify the command and reply path.

WeCom:

1. Create an intelligent bot in the WeCom admin console, choose API mode → long connection, and obtain the Bot ID and Secret.
2. In the system, create a "WeCom intelligent bot (long connection)" and fill in the Bot ID, Secret, and owner UserID.
3. After saving, the system establishes the long connection automatically; no platform URL verification is needed.
4. Add the bot to a group or one-to-one chat and send `/help` to verify.

## 2. Notification channels (one-way push)

Notification channels push monitor events to group chats. They need no public callback address, only the Webhook URL provided by the platform.

### 2.1 Comparison of the three group bots

| Platform | System type | Message format | Signature | Description |
| -------- | -------------------------- | -------- | ------------ | ---------------------------------------------- |
| WeCom | WeCom group bot | markdown | None | About 4096 bytes per message, truncated by the system; group bots can only send |
| Feishu | Feishu bot (custom bot) | interactive card | Optional signing secret | Signature verification can be enabled; recommended |
| DingTalk | DingTalk bot (custom bot) | markdown | Optional signing secret | Signing can be enabled; the system computes the signature per DingTalk rules |

Configuration entry: **Notification channels → New channel** in the left sidebar. Fill in the name, Webhook, optional signing secret, and check the events to subscribe to.

> Event notifications are sent through these group bot Webhooks by default; "Command bots" can also enable event notifications separately. The two are independent and can be used at the same time.

### 2.2 WeCom group bot

1. Open the WeCom group chat → group settings → group bots → add bot.
2. Copy the Webhook URL (usually of the form `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...`).
3. In the system's "Notification channels", choose **WeCom group bot**, paste the Webhook, and save.
4. Click "Send test" on the channel to confirm the message arrives in the group.

Notes:

- The Webhook itself is a credential; once leaked, anyone can post messages to the group. If leaked, remove the bot in the group and add it again.
- Group bots cannot receive commands such as `/add`; for commands use the "WeCom intelligent bot (long connection)".
- A single message is limited to about 4096 bytes; the system truncates automatically, so long lists may be cut off.
- Group bots are rate-limited; the system retries automatically when throttled.

### 2.3 Feishu custom bot

1. Open the Feishu group → group settings → group bots → add bot → custom bot.
2. Copy the Webhook URL (usually of the form `https://open.feishu.cn/open-apis/bot/v2/hook/...`).
3. It is recommended to choose **signature verification** in the security settings and copy the signing secret.
4. In the system's "Notification channels", choose **Feishu bot**, paste the Webhook, and fill in the signing secret if signing is enabled.
5. Save and send a test message.

Signing rules (already implemented in the system, no manual computation needed):

- The timestamp is in seconds.
- Use `timestamp + "\n" + secret` as the HMAC-SHA256 key, compute the signature over an empty string, and Base64-encode the result.
- The timestamp and signature are sent with the message body.

If you use "custom keywords" or an "IP allowlist" instead of signing, make sure the notification content contains the keyword, or add the server's egress IP to the allowlist.

### 2.4 DingTalk custom bot

1. Open the DingTalk group → group settings → smart group assistant → add bot → custom.
2. Copy the Webhook URL (usually of the form `https://oapi.dingtalk.com/robot/send?access_token=...`).
3. It is recommended to choose **signing** in the security settings and copy the signing secret.
4. In the system's "Notification channels", choose **DingTalk bot**, paste the Webhook, and fill in the signing secret if signing is enabled.
5. Save and send a test message.

Signing rules (already implemented in the system):

- The timestamp is in milliseconds.
- Use `secret` as the key, compute HMAC-SHA256 over `timestamp + "\n" + secret`, and Base64-encode the result.
- `timestamp` and `sign` are sent as URL query parameters.

If you use "custom keywords" or "IP address ranges" instead of signing, adjust the security settings accordingly. When throttled (e.g. error code `90037`), the system retries automatically.

### 2.5 Event subscription and retries

Notification channels can subscribe to the following event types:

| Event | Description |
| ------------------- | ---------------------------------------------- |
| `release` | Game / DLC officially released |
| `release_date` | An exact release date was obtained or the release date changed |
| `sale_start` | Discount reaches the monitor threshold |
| `sale_change` | Discount or price changes during a sale |
| `sale_end` | Discount ends and the base price is restored |
| `price_change` | Base price change or free-status flip outside a sale |
| `delisting_warning` | Steam news matched a delisting keyword (heuristic, needs manual confirmation) |
| `delisted` | Store confirmed unpurchasable on two consecutive checks |
| `restored` | Purchasable again |
| `check_error` | Check failed |

- With **no events selected**, all events except `check_error` are received by default.
- Failed deliveries are retried after 30 seconds → 2 minutes → 10 minutes → 1 hour → 6 hours → 24 hours, up to 6 times.
- Each channel card has a "Send test" button to verify the Webhook and signature configuration.

## 3. Command bots (two-way)

Command bots let users manage monitors with slash commands in Feishu / Lark, DingTalk, or WeCom chats. Feishu / Lark supports HTTP callbacks or WebSocket long connections, DingTalk supports HTTP callbacks or Stream long connections, and WeCom uses a WebSocket long connection; results are returned to the original conversation through the platform API or the long connection.

### 3.1 General behavior

- **Scope**: commands always operate on the data of the account that owns the bot. Even if another admin on the allowlist uses the bot, it modifies the bot owner's monitors.
- **Owner identifier**: `ownerPlatformUserId` only identifies the scanner / bot owner and does not grant command permission automatically.
- **Allowlist**: all platform users (including the owner ID) must be on the allowlist to run commands, with roles:
  - `admin`: can use all commands.
  - `viewer`: can only use `/help`, `/list`, `/price`, `/events`.
  - Feishu / Lark, DingTalk, and WeCom users not on the allowlist receive a one-time web authorization link and the bot does not run the original command; DingTalk supports this link as well.
- **Event notifications**: a bot can enable "Receive event notifications" separately on the edit page, pushing events to the conversation used by the most recently authorized user. This is independent of "Notification channels" and both can be enabled at once. Nothing is pushed when there is no recent conversation; see section 3.5 for details.
- **Message format**: only text messages are processed. Images, files, rich text, and card messages are ignored.
- **Command format**: starts with `/` or the full-width `／`; supports `/add@bot`, quoted arguments, and `--flag=value`.
- **Deduplication**: when the platform delivers the same message repeatedly, the system deduplicates by the platform event / message ID and processes it only once.
- **Rate limits**: at most 10 commands per minute per platform user, 30 per minute per conversation, and 60 per minute per bot; when throttled, the user is notified at most once per minute.
- **Asynchronous replies**: Feishu / Lark / DingTalk callbacks return success quickly, and DingTalk Stream / WeCom messages are received over the long connection; commands run in the background and results are returned through the platform API or long connection. Replies may appear with a small delay on the platform.
- **Multiple result selection**: when `/add` or `/adddlc` name search matches several results, the bot returns a numbered list; reply with the number (valid for 10 minutes), or send `/cancel` to cancel.
- **Quotas**: each account can create at most 3 bots; only 1 enabled bot is allowed per platform (Feishu and Lark international share the "Feishu" platform quota). For Feishu / Lark / DingTalk HTTP callback bots, the callback URL stops working immediately after the bot is disabled (returns 404); for long connection / Stream bots the connection is closed after the bot is disabled.

### 3.2 Feishu / Lark app bot (recommended)

> #### Why it is recommended
>
> Feishu/Lark offers a personal edition, which cleanly separates personal and work usage.



Feishu / Lark requires creating an **enterprise custom app**, enabling the bot capability, and subscribing to message events. Group custom bot Webhooks cannot receive commands. Feishu (China) uses `open.feishu.cn` / `accounts.feishu.cn`, while Lark international uses `open.larksuite.com` / `accounts.larksuite.com`; the system distinguishes them through the bot's "version" setting.

#### One-click creation by QR scan (recommended)

1. On "Command bots", click **Feishu / Lark QR** and choose "Feishu" or "Lark international" in the dialog.
2. Scan with the corresponding client; the page pre-fills the app name and only allows creating a new app.
3. After confirming creation, the system retrieves the App ID / App Secret, stores the scanner's `open_id` as the owner, and enables the long connection.
4. The QR code is valid for 10 minutes; it is rejected if the same platform already has an enabled bot or the quota is full.
5. Search for the app name in Feishu / Lark to start a one-to-one chat, or add the bot to a group and send `/help`.

> QR creation uses Feishu's official `PersonalAgent` template with bot capability, message permissions, and the `im.message.receive_v1` event preconfigured; events are received over a long connection. If your organization restricts QR creation, use the manual configuration below.
>
> If the Feishu QR code is scanned by a Lark tenant, the system automatically switches to `accounts.larksuite.com` to complete authorization.

#### Manual configuration

1. Open the [Feishu Open Platform](https://open.feishu.cn/app) or the [Lark Open Platform](https://open.larksuite.com/app) and create an enterprise custom app.
2. Enable **Bot** under "Add app capability".
3. Request message-related permissions under "Permission management":
   - `im:message.p2p_msg:readonly`: read one-to-one messages users send to the bot.
   - `im:message.group_at_msg:readonly`: receive group messages that @ the bot.
   - `im:message:send_as_bot`: send messages as the app.
   - If the console splits permissions by scenario, also request the permissions for reading message content and sending messages.
4. Create a "Feishu / Lark app bot" in the system, choosing the version and event receiving method:
   - **Long connection (recommended)**: choose "Receive events via long connection" under "Events and callbacks" on the platform and subscribe to `im.message.receive_v1`; no callback URL is needed.
   - **HTTP callback**: fill the `/webhooks/feishu/<slug>` shown by the system as the request URL; if encryption is required, fill in the Encrypt Key and Verification Token.
5. Create a version and publish the app; make sure users are covered by the "App availability" scope.
6. Add the bot to a group, or chat with the bot directly.

#### System-side fields

| Field | Required | Description |
| ------------------ | ----------------- | ---------------------------------------------------------------- |
| Name | Yes | For identification inside the system only |
| Version | Yes | Feishu (China) or Lark (international) |
| Event receiving method | Yes | HTTP callback / long connection; QR creation defaults to long connection |
| App ID | Recommended | Needed to obtain `tenant_access_token`, reply, and push events |
| App Secret | Recommended | Paired with the App ID |
| Encrypt Key | Depends on the platform when using HTTP callback | Must exactly match the Feishu / Lark console; required when encryption is enabled |
| Verification Token | Recommended for HTTP callback | Must match the platform; used to validate the event source |
| Owner platform user ID | Recommended | Use the Feishu / Lark `open_id` (usually starting with `ou_`); filled automatically by QR creation |
| API Base URL | No | For testing / proxying only; leave empty in production |

#### Callbacks, long connections, and signatures

- **HTTP callback**: when saving the event subscription URL, the platform sends a `url_verification` challenge and the system returns the `challenge`.
  - When an Encrypt Key is configured, the system validates the request header signature `SHA256(timestamp + nonce + encryptKey + rawBody)`, allows a ±300 second deviation, and then decrypts the ciphertext.
  - When a Verification Token is configured, the system validates the token in the event; a mismatch returns 401.
- **Long connection**: the service connects outbound to the Feishu / Lark long connection endpoint using the App ID / App Secret; events are pushed over the authenticated connection and need no signature verification, public address, or reverse proxy. The connection status is shown on the bot card.
- Only text messages in `im.message.receive_v1` are processed; messages sent by the app itself are ignored.
- Replies use the "reply message" API first, falling back to sending a message to `chat_id` on failure.
- In group chats you must **@ the bot** before entering a command; one-to-one chats can send commands directly.

#### Owner ID and allowlist

- Feishu / Lark events identify users by `open_id` first, so the allowlist should contain `open_id`, not a phone number, email, or name.
- QR creation stores the scanner's `open_id` in "Owner ID", but it is for identification only and does not grant command permission automatically; the first use still requires approving your own platform account through web authorization.
- For manual configuration you can check the event debug / callback logs, or ask the user to send a message first and then check the event details on the platform.

### 3.3 DingTalk bot (HTTP callback / Stream)

DingTalk requires creating an **enterprise internal bot**; the message receiving mode can be **Stream long connection** (recommended) or **HTTP callback / Outgoing**. DingTalk custom group bot Webhooks cannot receive commands.

#### Add by QR scan (recommended)

1. On the system's "Command bots" page, click **Add DingTalk bot by QR**.
2. Scan with the DingTalk mobile app, choose an organization, and fill in the bot information as prompted, then confirm creation.
3. The system retrieves the Client ID / Client Secret automatically, uses the Client ID as the Robot Code, and enables the Stream long connection; the QR code is valid for 10 minutes.
4. After creation you can search for the bot in DingTalk to start a one-to-one chat, or add it to a group; the scanner's `staffId` is for identification only, and members still need web authorization or allowlist membership.

> Scanning is rejected if the same platform already has an enabled bot or the bot quota is full; handle the old bot on the page first.
>
> Scanning uses DingTalk's official app registration page. If your organization restricts QR creation, or the registration page returns an error, you can still use the manual configuration below.

#### Manual configuration

1. Open the [DingTalk Open Platform](https://open.dingtalk.com/) and create an enterprise internal app.
2. Add **Bot** under "Add app capability".
3. Choose the message receiving mode:
   - **Stream mode (recommended)**: select Stream mode in the bot configuration and publish; no public callback address is needed.
   - **HTTP callback / Outgoing**: fill in the `/webhooks/dingtalk/<slug>` address shown by the system, and provide the App Secret for signature verification.
4. Create a "DingTalk bot" in the system, fill in the Client ID (App Key) and Client Secret (App Secret), and choose the same receiving mode.
5. To push event notifications, fill in the Robot Code (usually the same as the Client ID) and confirm the app has permission for the bot to send messages proactively.
6. Publish the app, add the bot to a group, and send `/help`.

#### System-side fields

| Field | Required | Description |
| --------------------------- | ----------------------- | ---------------------------------------------- |
| Name | Yes | For identification inside the system only |
| Message receiving mode | Yes | HTTP callback / Stream long connection; QR creation defaults to Stream |
| App Key (Client ID) | Required for Stream | DingTalk app Client ID; also needed for event notifications |
| App Secret (Client Secret) | Required for Stream / HTTP signature verification | Credential for the Stream connection; used to verify callback signatures for HTTP |
| Robot Code | Recommended for event notifications | Bot code; usually the same as the Client ID |
| Owner platform user ID | Recommended | Use the DingTalk `staffId` |
| API Base URL | No | For testing / proxying only; leave empty in production |

#### Message receiving and replies

- **Stream mode**: the service connects outbound to the DingTalk Stream gateway using the Client ID / Secret, so no public IP, domain, or callback address is needed; bot messages are pushed over the long connection, and the system ACKs immediately before running the command asynchronously.
- **HTTP callback**: DingTalk callback headers include `timestamp` (milliseconds) and `sign`; the system uses the App Secret as the key, computes HMAC-SHA256 over `timestamp + "\n" + App Secret`, and allows a ±1 hour deviation.
- Both modes only process text messages with `msgtype = text`.
- The user ID comes from `senderStaffId` first, then `senderId`; the owner ID and allowlist should contain the `staffId`.
- Replies use the `sessionWebhook` from the message body to send markdown and @ the command sender; this Webhook is usually valid for about 1.5 hours, so send the command again after it expires.
- The system deduplicates by DingTalk `msgId`; Stream mode additionally ACKs the push immediately to avoid repeated delivery by the platform.

#### Owner ID and allowlist

- Use `senderStaffId` (then `senderId`) from the callback event; you can find it in the event debug log of the open platform, or verify it in the contact member details.
- "Owner ID" is for identification only and does not grant command permission automatically; every DingTalk user needs web authorization or allowlist membership.
- QR creation does not always return the scanner's `staffId`, so you can add it manually; on first use, have the account that owns the bot log in to the web page and approve.

### 3.4 WeCom intelligent bot (long connection)

WeCom requires creating an **intelligent bot** and choosing **API mode → long connection**. WeCom group bot Webhooks can only send and cannot receive commands.

> Upgrade note: the legacy WeCom custom app callback (Token / EncodingAESKey / CorpID / AgentID) is no longer used for command bots. Existing bots must be updated under "Command bots" to use the intelligent bot's Bot ID / Secret and saved again.

#### Add by QR scan (recommended)

1. On the system's "Command bots" page, click **Add WeCom bot by QR**.
2. Scan with a WeCom account that has permission to create intelligent bots, and create and authorize the bot as prompted.
3. The system retrieves the Bot ID / Secret automatically, creates the bot, and establishes the long connection; the QR code is valid for 5 minutes.
4. After creation, have a member send a command and approve it by logging in to the web page with the account that owns the bot; the owner UserID is for identification only and does not grant permission automatically.

> Scanning is rejected if the same platform already has an enabled bot or the bot quota is full; handle the old bot on the page first.
>
> Scanning uses the official WeCom authorization page. If the account cannot create intelligent bots, or WeCom changes the page flow, you can still use the manual configuration below.

#### Manual configuration

1. Open the [WeCom admin console](https://work.weixin.qq.com/) or the WeCom client workbench and go to "Intelligent bots" → create bot.
2. In the creation flow, choose "Create in API mode" → "Use long connection".
3. Obtain and save the **Bot ID** and **Secret**. The Secret is usually shown only once and can be regenerated if lost.
4. Create a "WeCom intelligent bot (long connection)" in the system and fill in the Bot ID, Secret, and owner UserID.
5. Add the bot to a group or one-to-one chat; in groups, **@ the bot** and send `/help`.
6. No callback URL, Token, EncodingAESKey, or CorpID is required; the service connects outbound to `wss://openws.work.weixin.qq.com`.

#### System-side fields

| Field | Required | Description |
| ----------------- | -------- | ---------------------------------------------------------------------- |
| Name | Yes | For identification inside the system only |
| Bot ID | Yes | Unique identifier of the intelligent bot |
| Secret | Yes | Long-connection-only Secret, used for `aibot_subscribe` authentication |
| Owner platform user ID | Recommended | The member UserID in the WeCom contact list; the `from.userid` in actual bot callbacks takes precedence |

#### Long connection mechanics

- The service connects outbound to `wss://openws.work.weixin.qq.com`, which suits intranet deployments and needs no fixed public IP.
- After connecting, it sends `aibot_subscribe` with the Bot ID + Secret for authentication, then sends a `ping` heartbeat every 30 seconds.
- User messages are pushed as plaintext `aibot_msg_callback`, so no decryption is needed; the system only processes `msgtype = text`.
- Replies are sent as markdown via `aibot_respond_msg` with the `req_id` from the callback; replies for the same `req_id` are sent sequentially.
- An intelligent bot allows only one valid long connection at a time; a new connection kicks the old one, and multiple instances interrupt each other.
- Disconnections reconnect with exponential backoff; if authentication keeps failing or the connection is replaced by a new instance, the bot card shows a long connection error.
- Group messages have the leading `@bot` removed before slash command parsing.
- Replies are possible within 24 hours after the message callback; the system runs commands in a background queue, and long commands usually take a few seconds.
- With bot event notifications enabled, the system proactively pushes to the most recent conversation over the same long connection using `aibot_send_msg`; the user must have messaged the bot first.

#### Owner ID and allowlist

- Fill in the **UserID** (member account) from the WeCom contact list; do not use a name, phone number, or external contact ID.
- If the bot creator is not an enterprise super admin, `from.userid` may be an encrypted userid under the enterprise entity; configure the owner and allowlist based on the actual callback events.

#### Unauthorized users and web authorization

- When a WeCom user is not on the allowlist, the bot replies with a one-time web authorization link (`PUBLIC_BASE_URL/authorize/<token>`), valid for 30 minutes.
- The bot owner logs in to the link page with their own web account, verifies the platform user ID (plus any available nickname and conversation), chooses `viewer` or `admin`, then approves or rejects.
- Users other than the bot owner can only view the request after logging in and cannot approve it themselves; forward the link to the bot owner instead.
- The authorization link stops working after being handled once; other pending links for the same user are updated accordingly. After expiry, have the user send any command again to generate a new link.
- All members (including the scanner) need permission through web authorization or the allowlist; if you want full command permissions for yourself, choose `admin` when approving.
- `PUBLIC_BASE_URL` must be reachable from the browser; if the link does not open, check the reverse proxy and that environment variable.

#### Connection status

The bot card shows the long connection status:

- **Connecting**: establishing or automatically re-establishing the connection.
- **Long connection connected**: authentication succeeded and commands can be received.
- **Long connection error**: invalid credentials, missing Bot ID / Secret, unreachable network, authentication failure, or the connection was replaced by another instance.
- **Long connection disabled**: the bot is disabled.

If the status stays in error, check the Bot ID / Secret, whether the server's outbound firewall allows `wss://openws.work.weixin.qq.com:443`, and whether another instance uses the same Bot ID.

### 3.5 Bot event notifications

After checking **Receive event notifications** on the "Command bots" edit page, the bot additionally receives events such as releases, discounts, and delistings. This is a separate configuration from notification channels, and both can be enabled at once.

- **Notification target**: the conversation most recently used by an allowlisted member of the bot. The system updates the target only after an authorized user successfully sends a command; unauthorized users do not change the notification target.
- **Precondition**: the target bot must have received at least one command from an authorized user, otherwise no events are delivered. The bot card shows "no recent conversation recorded yet".
- **Event scope**: all events, including check errors; filtering event types per bot is not supported.
- **Group bots in notification channels still send according to their own event subscriptions; the two do not affect each other.**

Additional requirements per platform:

- **Feishu / Lark**: requires the App ID / App Secret and the permission to send messages to conversations as the app. Events are sent to the `chat_id` of the most recent conversation; both HTTP callback and long connection modes work.
- **DingTalk**: requires the App Key, App Secret, and Robot Code, plus permission for the bot to send messages proactively. Group chats use `openConversationId`, and one-to-one chats use the sender's `staffId`.
- **WeCom**: pushes to the most recent conversation over the long connection with `aibot_send_msg`; one-to-one chats use `chat_type=1`, group chats use `chat_type=2`. The user must have had a conversation with the bot first.

> Delivery is cancelled or fails if the bot is disabled, event notifications are turned off, the most recent conversation is deleted, or the bot is removed from the group; have an authorized user send a command again to refresh the target conversation.

## 4. Command reference

```text
/help
/add <appid | store link | name> [--discount N] [--note text] [--force]
/adddlc <base game appid | link | name> [--max 50]
/remove <id | appid | name>
/pause <id | appid | name>
/resume <id | appid | name>
/check <id | appid | name>
/price <id | appid | name>
/list [--all] [--sale] [--paused] [--page N]
/events [--item id] [--limit 10]
/cancel
```

Notes:

- `/add` can search the Steam store directly; when a name search returns several results, reply with the number to choose.
- `--discount N` sets the discount notification threshold (0–100); when omitted, the account default is used.
- `--force` is for cases where the item cannot be fetched in the current region but you still want to add it for news warnings only.
- `/adddlc` imports all DLC for a base game, at most 50 per call.
- `/check` bypasses the cache to check immediately and record events, subject to Steam rate limits.
- `/list` hides paused items by default; `--all` shows everything, `--sale` shows only items on sale, `--paused` shows only paused items.
- `/events` shows the latest 10 by default, up to 20.
- Viewer permission is limited to `/help`, `/list`, `/price`, `/events`.

## 5. Troubleshooting

| Symptom | Possible cause | Action |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Feishu / Lark / DingTalk fails to save the callback URL | Service not publicly reachable, invalid certificate, wrong `PUBLIC_BASE_URL` | Access the callback domain over mobile data; confirm the HTTPS certificate chain is complete; confirm the bot is created and enabled |
| Feishu / Lark / DingTalk callback returns 404 | Bot disabled or deleted, or wrong `<slug>` | Copy the latest callback URL from the "Command bots" page; enable the bot |
| Feishu / Lark reports a challenge failure / 401 | Verification Token or Encrypt Key mismatch; the proxy rewrote the request body | Re-check both sides; disable request body compression / rewriting; preserve the `X-Lark-*` headers |
| Feishu / Lark bot does not respond after encryption is enabled | The platform enabled an Encrypt Key but the system has none, so the ciphertext cannot be parsed; or the Verification Token check returns 401 directly | Enter the same Encrypt Key and Verification Token in the system, or disable platform encryption and save again |
| Feishu / Lark receives messages but cannot reply | App ID / App Secret missing, or missing message sending permission | Complete the credentials; request and publish the message sending permission on the open platform |
| Feishu / Lark long connection stays connecting / errors | Wrong App ID / App Secret; the app did not enable "Receive events via long connection"; the organization restricts QR creation | Verify the credentials; switch "Events and callbacks" to long connection and publish a version; or switch to HTTP callback |
| Cannot find the Feishu / Lark bot after scanning | App not published or the availability scope excludes the member | Create and publish a version on the open platform and adjust the availability scope; search by app name |
| Scanned a Feishu QR code but a Lark app was created | The scanning account belongs to a Lark tenant, so the system switched the authorization domain | Expected behavior; search for the app name in Lark |
| DingTalk callback 401 | Wrong App Secret; proxy removed headers; server clock skew over 1 hour | Verify the app App Secret (not the signing secret); preserve `timestamp` and `sign`; sync NTP |
| DingTalk reply times out / fails | `sessionWebhook` has expired | Send the command again; make sure the callback completes within seconds |
| DingTalk Stream never connects / errors | Wrong Client ID / Secret; the bot did not select Stream mode; the app is not published; the server cannot reach `api.dingtalk.com` outbound | Verify the credentials; select Stream in the bot configuration and publish a version; check outbound networking |
| DingTalk QR scan reports authorization failure | The scanning account lacks developer permission; the QR code expired; the selected organization does not allow app creation; the authorization page template failed to load | Confirm the account has developer permission in the target organization; regenerate the QR code; try an organization with permission; if it still fails, check the "DingTalk scan authorization failed" reason in the service logs |
| DingTalk bot does not reply after scanning | App not published or the availability scope excludes the member; the bot was not added to the conversation; the Stream connection is not established | Publish the app and adjust the availability scope; check the connection status on the bot card; send the command again |
| DingTalk / Feishu user is told they are unauthorized | The platform user is not on the allowlist and has not passed web authorization | Have the user send any command to get an authorization link, then approve it by logging in to the web page with the account that owns the bot, or add the user to the allowlist directly |
| WeCom long connection is not connected / errors | Wrong Bot ID or Secret; the server cannot reach `openws.work.weixin.qq.com:443` outbound; another instance uses the same bot; the bot is disabled | Verify the Bot ID / Secret; check the outbound firewall and proxy; confirm there is no duplicate deployment; check the status and error on the bot card |
| WeCom messages get no reply | The long connection is closed; the message is outside the 24-hour reply window; the bot was disabled or deleted during processing | Check the long connection status; send the command again; confirm the bot stays enabled |
| WeCom reports the connection was replaced | A new connection was established with the same Bot ID and WeCom kicked the old one | Keep only one running instance per bot; stop the duplicate deployment, or disable and re-enable the bot in the system |
| Commands get no response | The bot was not @-mentioned in a group; the message is not text; it does not start with `/`; the user is not on the allowlist | @ the bot in the group; send `/help`; add the platform user ID to the allowlist |
| The scanner has no command permission either | The owner ID is for identification only and no longer grants permission implicitly | Approve your own platform account on the web authorization page, or have the account that owns the bot add your platform ID to the allowlist |
| Bot creation conflict | The same platform already has an enabled bot | Disable the old bot first, then enable the new one |
| Notification channel test fails | Invalid Webhook, wrong signing secret, keyword / IP allowlist restrictions | Copy the Webhook again; verify the signing secret; check the platform security settings |
| No event notifications in the group at all | Channel disabled, event types not selected, group bot removed | Check the channel status and event subscriptions; send a test message again |
| Bot does not push event notifications | "Receive event notifications" not enabled; no recent authorized conversation; DingTalk missing App Key / Robot Code; bot disabled | Edit the bot and enable notifications; have an authorized user send a command first; complete the DingTalk credentials; check the delivery records |
| Feishu / Lark / DingTalk pushes the same message repeatedly | The platform did not receive an ACK in time or the network jittered | The system deduplicates by message ID; make sure callbacks return within 10 seconds |

### Debugging tips

1. First use **Simulate command** on the "Command bots" card to execute locally as the bot owner and confirm the command logic and quotas work.
2. Then use **Send test** in "Notification channels" to verify the Webhook and signature.
3. Finally send `/help` in the platform chat to confirm the callback / long connection, permissions, and reply path.
4. Check the container logs: `docker compose logs -f steam-monitor`, paying attention to logs related to `wecom`, `webhook`, `inbound`, and `delivery`.

## 6. Security recommendations

- Treat Feishu / Lark / DingTalk callback URLs, group bot Webhooks, and the WeCom Bot ID / Secret as credentials; do not commit them to public repositories or post them in public groups.
- For Feishu / Lark HTTP callbacks, enable Encrypt Key + Verification Token; long connection credentials must also be kept secret. DingTalk HTTP callbacks must fill in the App Secret for signature verification, and Stream mode must protect the Client Secret as well; WeCom must protect the Bot ID and long connection Secret.
- Follow least privilege for the allowlist: use `viewer` for regular members and `admin` only for administrators.
- Do not expose the SQLite file to the public internet; back up the database regularly, and back up the `APP_SECRET` in `.env` at the same time.
- After changing `PUBLIC_BASE_URL` or switching domains, update the callback URLs in the Feishu / Lark / DingTalk consoles promptly; long connection mode is unaffected.
- If you suspect credentials were leaked: reset the App Secret / Encrypt Key for Feishu / Lark, reset the Client Secret for DingTalk, regenerate the intelligent bot Secret for WeCom, and re-enter them in the system.
