# Feishu / Lark、DingTalk、WeCom 連携ガイド

本書では、Feishu / Lark、DingTalk、WeCom を Steam Games Monitor に連携する方法を説明します。プロジェクトには互いに代替できない 2 つの機能があるため、まず目的を確認してください：

| 目的 | プラットフォーム側で作成するもの | システムの画面 | 方向 |
| --- | --- | --- | --- |
| 発売、セール、削除などのイベント通知を受け取る | グループカスタムボット / グループボット Webhook | **通知チャネル** | 単方向：システム → グループ |
| チャットで `/add`、`/list` などのコマンドを送信する | Feishu / Lark 企業内アプリ / DingTalk 企業内ボット（Outgoing） / WeCom スマートボット（常時接続） | **コマンドボット** | 双方向：プラットフォーム → システム → プラットフォーム |

> グループボットの Webhook は通常、メッセージの送信のみが可能でコマンドは受信できません。Feishu / Lark と DingTalk はいずれも QR コードでアプリをワンクリック作成でき、HTTP コールバックまたは常時接続を選択できます。WeCom はスマートボットを作成し、常時接続を使用する必要があります。
>
> 通知チャネルとコマンドボットは 2 つの独立した設定です。同じプラットフォームで通知のみ、コマンドのみ、あるいは両方を設定できます。

## 1. 共通の準備

### 1.1 公開 HTTPS と PUBLIC_BASE_URL（HTTP コールバックモード）

**HTTP コールバック** を使用する Feishu / Lark / DingTalk は、プラットフォームからサーバーへメッセージをプッシュする必要があるため、次を満たす必要があります：

- サービスがインターネットからアクセス可能で、プラットフォームが認める **HTTPS** アドレスを使用していること。
- `.env` の `PUBLIC_BASE_URL` がブラウザから実際にアクセスするアドレスと一致していること（例：`https://steam.example.com`）。
- 既定の `http://localhost:8787` を使用しないでください。そうしないと、システムが生成するコールバックアドレスにプラットフォームからアクセスできません。
- 専用ドメインまたはサブドメインの使用を推奨します。コールバックパスは `/webhooks/...` に固定されているため、追加のリライトが必要なサブパスにはデプロイしないでください。

システムに表示されるコールバックアドレスは次のルールで生成されます：

```text
Feishu / Lark  https://<PUBLIC_BASE_URL のドメイン>/webhooks/feishu/<slug>
DingTalk       https://<PUBLIC_BASE_URL のドメイン>/webhooks/dingtalk/<slug>
```

`<slug>` はボット作成時にランダムに生成され、ボットごとに異なります。`PUBLIC_BASE_URL` を変更するとコールバックアドレスも変わるため、プラットフォームの管理画面も合わせて更新する必要があります。

> Feishu / Lark の**常時接続モード**、DingTalk の **Stream モード**、WeCom スマートボットは、いずれもサーバー側からアウトバウンド接続を確立するため、公開コールバックアドレス、公開 IP、Token、EncodingAESKey は不要です。QR コードで作成した Feishu / Lark アプリと DingTalk ボットは、既定で常時接続を使用します。
>
> ただし、`PUBLIC_BASE_URL` はボットの所有者がブラウザからアクセスできる必要があります。未承認ユーザーに送られる Web 認可リンクはこのアドレスを使用します。

### 1.2 リバースプロキシの要件

Nginx、Caddy、Traefik、またはクラウドロードバランサーは次を満たす必要があります（Feishu / Lark / DingTalk の HTTP コールバックにのみ影響します）：

- **リクエストボディをそのまま転送**してください。JSON を再シリアライズしたり、内容を圧縮・変更したりしないでください。Feishu / Lark と DingTalk の署名は元のリクエストボディに基づきます。
- プラットフォームのリクエストヘッダーを保持してください：Feishu の `X-Lark-Request-Timestamp`、`X-Lark-Request-Nonce`、`X-Lark-Signature`、DingTalk の `timestamp`、`sign`。
- クエリパラメータを保持し、署名パラメータを失わないでください。
- `/webhooks/*` にログイン、Basic Auth、HTML リダイレクト、WAF のインタラクティブ検証を追加しないでください。
- リクエストボディの上限は少なくとも 1 MB、読み取りタイムアウトは 10 秒以上にしてください。
- 信頼された TLS 証明書を使用してください。プラットフォームは証明書チェーンを検証します。

Feishu / Lark の常時接続、DingTalk の Stream、WeCom の常時接続はリバースプロキシを経由しません。サーバーが対応するプラットフォームへアウトバウンドアクセスできることだけが必要です（Lark は `open.larksuite.com`、DingTalk Stream は `api.dingtalk.com` を使用します）。

### 1.3 時刻同期とシークレット

- サーバーで NTP 時刻同期を有効にしてください。Feishu / Lark の署名は ±300 秒、DingTalk の Outgoing コールバックは ±1 時間のずれを許容します。
- `APP_SECRET`（32 文字以上）は、チャネルとボットの認証情報を暗号化して保存するために使用します。**むやみに変更したり失ったりしないでください**。変更すると、保存済みの App Secret、ボット Secret、Encrypt Key などが復号できなくなり、再入力が必要になります。
- ボットの認証情報は SQLite に AES-256-GCM で暗号化して保存されます。API と画面には平文が表示されず、編集時に空欄にすると元の値が保持されます。

### 1.4 推奨する作成手順

Feishu / Lark（QR コード、推奨）：

1. 「コマンドボット」で「Feishu / Lark QR コード」をクリックし、Feishu または Lark 国際版を選択して QR コードを読み取ります。
2. プラットフォームのページでアプリを作成して確認します。システムは App ID / App Secret と所有者の `open_id` を自動的に書き込み、常時接続を有効にします。
3. Feishu / Lark でアプリ名を検索して 1 対 1 チャットを開始するか、ボットをグループチャットに追加します。
4. `/help` を送信して、コマンドと返信の経路を確認します。

Feishu / Lark（手動）：

1. システムでボットを作成し、バージョン（Feishu / Lark）とイベント受信方式（HTTP コールバック / 常時接続）を選択します。
2. HTTP コールバック：コールバックアドレスをコピーしてプラットフォームの管理画面に入力し、Encrypt Key / Verification Token を設定します。常時接続：プラットフォームで「常時接続でイベントを受信」を選択します。
3. `im.message.receive_v1` を購読し、メッセージの読み取りと送信の権限を申請します。
4. アプリを公開し、ボットをグループに追加するか、利用範囲を設定します。
5. `/help` を送信して確認します。

DingTalk（QR コード、推奨）：

1. 「コマンドボット」で「DingTalk QR コードで追加」をクリックし、スマートフォンの DingTalk で QR コードを読み取って作成を確認します。
2. システムが Client ID / Client Secret を自動的に書き込み、Client ID を Robot Code として Stream 常時接続を有効にします。
3. DingTalk でボットを検索して 1 対 1 チャットを開始するか、ボットをグループチャットに追加します。
4. `/help` を送信して確認します。

DingTalk（手動）：

1. システムでボットを作成し、メッセージ受信モードを選択して、コールバックアドレスをコピーします（HTTP モード）。
2. プラットフォームの管理画面でアプリ / ボットを作成し、コールバックアドレスとシークレットを入力するか、ボット設定で Stream モードを選択します。
3. プラットフォームでコールバックを保存する際、通常は URL 検証が実行されます。システムが起動済みで、ボットが有効になっていることを確認してください。
4. プラットフォームでアプリを公開し、ボットをグループに追加するか、利用範囲を設定します。
5. `/help` を送信して、コマンドと返信の経路を確認します。

WeCom：

1. WeCom 管理コンソールでスマートボットを作成し、API モード → 常時接続を選択して Bot ID と Secret を取得します。
2. システムで「WeCom スマートボット（常時接続）」を作成し、Bot ID、Secret、所有者 UserID を入力します。
3. 保存するとシステムが自動的に常時接続を確立します。プラットフォーム側の URL 検証は不要です。
4. ボットをグループチャットまたは 1 対 1 チャットに追加し、`/help` を送信して確認します。

## 2. 通知チャネル（単方向プッシュ）

通知チャネルは、監視イベントをグループチャットにプッシュするためのものです。公開コールバックアドレスは不要で、プラットフォームが提供する Webhook URL だけが必要です。

### 2.1 3 種類のグループボットの比較

| プラットフォーム | システムの種類 | メッセージ形式 | 署名 | 説明 |
| --- | --- | --- | --- | --- |
| WeCom | WeCom グループボット | markdown | なし | 1 メッセージあたり約 4096 バイトで、システムが切り詰めます。グループボットは送信のみ可能 |
| Feishu | Feishu ボット（カスタムボット） | インタラクティブカード | 署名シークレット（任意） | 署名検証を有効にできます。有効化を推奨 |
| DingTalk | DingTalk ボット（カスタムボット） | markdown | 署名シークレット（任意） | 「加签」（署名）を有効にできます。システムが DingTalk のルールで署名を計算 |

設定入口：左側の **通知チャネル → チャネルを新規作成**。名前、Webhook、任意の署名シークレットを入力し、購読するイベントを選択します。

> イベント通知は既定でここのグループボット Webhook から送信されます。「コマンドボット」でも個別にイベント通知を有効にできます。両者は独立しており、同時に使用できます。

### 2.2 WeCom グループボット

1. WeCom のグループチャットを開く → グループ設定 → グループボット → ボットを追加。
2. Webhook アドレスをコピーします（通常は `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...` の形式）。
3. システムの「通知チャネル」で **WeCom グループボット** を選択し、Webhook を貼り付けて保存します。
4. チャネルの「テスト送信」をクリックし、グループにメッセージが届くことを確認します。

注意：

- Webhook 自体が認証情報です。漏洩すると誰でもグループにメッセージを送信できます。漏洩した場合はグループ内でボットを削除し、再追加してください。
- グループボットは `/add` などのコマンドを受信できません。コマンドが必要な場合は「WeCom スマートボット（常時接続）」を使用してください。
- 1 メッセージあたりの上限は約 4096 バイトで、システムが自動的に切り詰めるため、長いリストは一部表示されないことがあります。
- グループボットにはレート制限があり、制限に達した場合はシステムが自動的に再試行します。

### 2.3 Feishu カスタムボット

1. Feishu のグループを開く → グループ設定 → グループボット → ボットを追加 → カスタムボット。
2. Webhook アドレスをコピーします（通常は `https://open.feishu.cn/open-apis/bot/v2/hook/...` の形式）。
3. セキュリティ設定で **署名検証** を選択し、署名シークレットをコピーすることを推奨します。
4. システムの「通知チャネル」で **Feishu ボット** を選択し、Webhook を貼り付けます。署名を有効にした場合は署名シークレットを入力します。
5. 保存後にテストメッセージを送信します。

署名ルール（システム側で実装済みのため、手動計算は不要です）：

- タイムスタンプは秒単位です。
- `timestamp + "\n" + secret` を HMAC-SHA256 のキーとして空文字列の署名を計算し、結果を Base64 でエンコードします。
- タイムスタンプと署名はメッセージボディと一緒に送信されます。

署名の代わりに「カスタムキーワード」や「IP ホワイトリスト」を使用する場合は、通知内容にキーワードが含まれていることを確認するか、サーバーの送信元 IP をホワイトリストに追加してください。

### 2.4 DingTalk カスタムボット

1. DingTalk のグループを開く → グループ設定 → スマートグループアシスタント → ボットを追加 → カスタム。
2. Webhook アドレスをコピーします（通常は `https://oapi.dingtalk.com/robot/send?access_token=...` の形式）。
3. セキュリティ設定で **「加签」** を選択し、署名シークレットをコピーすることを推奨します。
4. システムの「通知チャネル」で **DingTalk ボット** を選択し、Webhook を貼り付けます。「加签」を有効にした場合は署名シークレットを入力します。
5. 保存後にテストメッセージを送信します。

署名ルール（システム側で実装済み）：

- タイムスタンプはミリ秒単位です。
- `secret` をキーとして `timestamp + "\n" + secret` の HMAC-SHA256 を計算し、結果を Base64 でエンコードします。
- `timestamp` と `sign` は URL のクエリパラメータとして送信されます。

「加签」の代わりに「カスタムキーワード」や「IP アドレス範囲」を使用する場合は、セキュリティ設定を適宜調整してください。レート制限（エラーコード `90037` など）に達した場合は、システムが自動的に再試行します。

### 2.5 イベント購読と再試行

通知チャネルでは、購読するイベントタイプを選択できます：

| イベント | 説明 |
| --- | --- |
| `release` | ゲーム / DLC の正式発売 |
| `release_date` | 正確な発売日を取得、または発売日が変更 |
| `sale_start` | 割引が監視しきい値に到達 |
| `sale_change` | セール中の割引率または価格の変化 |
| `sale_end` | 割引の終了、定価への復帰 |
| `price_change` | 非セール状態での定価変更、または無料状態の反転 |
| `delisting_warning` | Steam ニュースが削除キーワードに一致（ヒューリスティック、要確認） |
| `delisted` | 2 回連続でストアからの購入不可を確認 |
| `restored` | 購入可能に復旧 |
| `check_error` | チェック失敗 |

- **イベントを何も選択しない**場合、既定で `check_error` 以外のすべてのイベントを受信します。
- 送信に失敗した場合は 30 秒 → 2 分 → 10 分 → 1 時間 → 6 時間 → 24 時間の間隔で再試行し、最大 6 回です。
- 各チャネルのカードに「テスト送信」があり、Webhook と署名設定の検証に使用できます。

## 3. コマンドボット（双方向）

コマンドボットを使うと、ユーザーは Feishu / Lark、DingTalk、WeCom のチャットでスラッシュコマンドを送信して監視項目を管理できます。Feishu / Lark は HTTP コールバックまたは WebSocket 常時接続、DingTalk は HTTP コールバックまたは Stream 常時接続、WeCom は WebSocket 常時接続に対応し、結果はそれぞれプラットフォーム API または常時接続を通じて元の会話に返信されます。

### 3.1 共通の動作

- **作用範囲**：コマンドは常にボットの所有アカウントのデータに作用します。許可リスト内の他の管理者がボットを使用しても、変更されるのはボット所有者の監視項目です。
- **所有者の識別**：`ownerPlatformUserId` は QR コードを読み取った人 / ボット所有者の識別にのみ使用され、コマンド権限を自動的に付与することはありません。
- **許可リスト**：すべてのプラットフォームユーザー（所有者 ID を含む）は、コマンドを実行するために許可リストに追加される必要があります。ロールは次のとおりです：
  - `admin`：すべてのコマンドを使用できます。
  - `viewer`：`/help`、`/list`、`/price`、`/events` のみ使用できます。
  - 許可リストにない Feishu / Lark、DingTalk、WeCom のユーザーにはワンタイムの Web 認可リンクが送られ、ボットは元のコマンドを実行しません。DingTalk もこのリンクに対応しています。
- **イベント通知**：ボットは編集ページで個別に「イベント通知を受信」を有効にでき、イベントを最後に承認済みユーザーが使用した会話にプッシュします。「通知チャネル」とは独立しており、同時に有効にできます。直近の会話がない場合はプッシュされません。詳細は 3.5 節を参照してください。
- **メッセージ形式**：現在はテキストメッセージのみを処理します。画像、ファイル、リッチテキスト、カードメッセージは無視されます。
- **コマンド形式**：`/` または全角の `／` で始まります。`/add@ボット`、引用符付きの引数、`--flag=value` に対応しています。
- **重複排除**：プラットフォームが同じメッセージを重複して配信した場合、システムはプラットフォームのイベント / メッセージ ID で重複排除し、1 回だけ処理します。
- **レート制限**：各プラットフォームユーザーは 1 分あたり最大 10 コマンド、各会話は 1 分あたり最大 30 コマンド、各ボットは 1 分あたり最大 60 コマンドです。制限に達した場合、通知は 1 分あたり最大 1 回です。
- **非同期の返信**：Feishu / Lark / DingTalk のコールバックはまず成功を迅速に返し、DingTalk の Stream / WeCom のメッセージは常時接続で受信します。コマンドはバックグラウンドで実行され、結果はプラットフォーム API または常時接続で返信されます。プラットフォームに返信が表示されるまで多少の遅延が生じることがあります。
- **複数結果の選択**：`/add`、`/adddlc` で名前検索が複数の結果に一致した場合、ボットは番号付きリストを返します。番号をそのまま返信する（10 分間有効）か、`/cancel` を送信してキャンセルします。
- **クォータ**：各アカウントは最大 3 個のボットを作成できます。同じプラットフォームで有効にできるボットは 1 個のみです（Feishu と Lark 国際版は「Feishu」プラットフォームの枠を共有します）。Feishu / Lark / DingTalk の HTTP コールバックボットは、無効化するとコールバックアドレスが直ちに無効になります（404 を返します）。常時接続 / Stream ボットは、無効化すると接続が切断されます。

### 3.2 Feishu / Lark アプリボット（推奨）

> #### 推奨理由
>
> Feishu / Lark は個人版を利用できるため、プライベートと仕事をうまく分けられます。



Feishu / Lark では**企業内アプリ**を作成し、ボット機能を有効にしてメッセージイベントを購読する必要があります。グループカスタムボット Webhook はコマンドを受信できません。Feishu（中国版）は `open.feishu.cn` / `accounts.feishu.cn`、Lark 国際版は `open.larksuite.com` / `accounts.larksuite.com` を使用します。システム内ではボット設定の「バージョン」で区別します。

#### QR コードによるワンクリック作成（推奨）

1. 「コマンドボット」で **Feishu / Lark QR コード** をクリックし、ダイアログで「Feishu」または「Lark 国際版」を選択します。
2. 対応するクライアントで QR コードを読み取ります。ページにはアプリ名が事前入力され、新規アプリの作成のみが許可されます。
3. 作成を確認すると、システムは App ID / App Secret を自動取得し、読み取った人の `open_id` を所有者として書き込み、常時接続を有効にします。
4. QR コードの有効期限は 10 分です。同じプラットフォームに有効なボットが既にある場合、またはクォータが上限に達している場合は拒否されます。
5. Feishu / Lark でアプリ名を検索して 1 対 1 チャットを開始するか、ボットをグループチャットに追加して `/help` を送信します。

> QR コード作成では Feishu 公式の `PersonalAgent` テンプレートを使用し、ボット機能、メッセージ権限、`im.message.receive_v1` イベントが事前に設定され、イベント受信方式は常時接続になります。企業の制限で QR コード作成を使用できない場合は、下記の手動設定を利用できます。
>
> Feishu の QR コードを Lark テナントが読み取った場合、システムは自動的に `accounts.larksuite.com` に切り替えて認可を続行します。

#### 手動設定

1. [Feishu 開発者プラットフォーム](https://open.feishu.cn/app)または [Lark 開発者プラットフォーム](https://open.larksuite.com/app)を開き、企業内アプリを作成します。
2. 「アプリ機能を追加」で **ボット** を有効にします。
3. 「権限管理」でメッセージ関連の権限を申請します：
   - `im:message.p2p_msg:readonly`：ユーザーがボットに送信した 1 対 1 チャットのメッセージを読み取ります。
   - `im:message.group_at_msg:readonly`：グループチャットでボットを @ メンションしたメッセージを受信します。
   - `im:message:send_as_bot`：アプリとしてメッセージを送信します。
   - 管理画面でシナリオごとに権限が分割されている場合は、メッセージ内容の読み取りとメッセージ送信に対応する権限も併せて申請してください。
4. システムで「Feishu / Lark アプリボット」を作成し、バージョンとイベント受信方式を選択します：
   - **常時接続（推奨）**：プラットフォームの「イベントとコールバック」で「常時接続でイベントを受信」を選択し、`im.message.receive_v1` を購読します。コールバックアドレスは不要です。
   - **HTTP コールバック**：システムに表示される `/webhooks/feishu/<slug>` をリクエストアドレスとして入力します。暗号化が必要な場合は Encrypt Key と Verification Token を入力します。
5. バージョンを作成してアプリを公開します。「アプリの利用範囲」で利用者が利用可能であることを確認してください。
6. ボットをグループチャットに追加するか、ボットと直接 1 対 1 チャットします。

#### システム側のフィールド

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| 名前 | はい | システム内での識別のみに使用 |
| バージョン | はい | Feishu（中国版）または Lark（国際版） |
| イベント受信方式 | はい | HTTP コールバック / 常時接続。QR コード作成では既定で常時接続 |
| App ID | 入力推奨 | `tenant_access_token` の取得、返信、イベントプッシュに必要 |
| App Secret | 入力推奨 | App ID とペアで使用 |
| Encrypt Key | HTTP コールバック時はプラットフォーム次第 | Feishu / Lark の管理画面と完全に一致させる必要があります。暗号化を有効にする場合は必須 |
| Verification Token | HTTP コールバック時は推奨 | プラットフォームと一致させます。イベントの送信元検証に使用 |
| 所有者プラットフォームユーザー ID | 入力推奨 | Feishu / Lark の `open_id`（通常 `ou_` で始まる）を入力します。QR コード作成では自動入力 |
| API Base URL | いいえ | テスト / プロキシ専用。本番環境では空欄 |

#### コールバック、常時接続、署名

- **HTTP コールバック**：プラットフォームがイベント購読アドレスを保存する際に `url_verification` チャレンジを送信し、システムは `challenge` を返します。
  - Encrypt Key が設定されている場合、システムはリクエストヘッダーの署名 `SHA256(timestamp + nonce + encryptKey + rawBody)` を検証し、±300 秒のずれを許容したうえで暗号文を復号します。
  - Verification Token が設定されている場合、システムはイベント内の token を検証します。一致しない場合は 401 を返します。
- **常時接続**：サーバーは App ID / App Secret を使用して Feishu / Lark の常時接続エンドポイントに能動的に接続します。イベントは認証済み接続でプッシュされるため、署名検証、公開アドレス、リバースプロキシは不要です。接続状態はボットのカードに表示されます。
- `im.message.receive_v1` のテキストメッセージのみを処理し、アプリ自身が送信したメッセージは無視します。
- 返信はまず「メッセージ返信」API を呼び出します。失敗した場合は `chat_id` へのメッセージ送信にフォールバックします。
- グループチャットでは **ボットを @ メンション** してからコマンドを入力する必要があります。1 対 1 チャットではそのまま送信できます。

#### 所有者 ID と許可リスト

- Feishu / Lark のイベントではユーザー識別に `open_id` を優先して使用するため、許可リストには `open_id` を入力してください。電話番号、メールアドレス、氏名は入力しないでください。
- QR コード作成では読み取った人の `open_id` が「所有者 ID」に書き込まれますが、これは識別のみに使用され、コマンド権限は自動的に付与されません。初回利用時は、自分のプラットフォームアカウントを Web 認可で承認する必要があります。
- 手動設定の場合は、イベントのデバッグ / コールバックログを確認するか、ユーザーに先に 1 通メッセージを送信させてからプラットフォームのイベント詳細を確認してください。

### 3.3 DingTalk ボット（HTTP コールバック / Stream）

DingTalk では**企業内ボット**を作成する必要があり、メッセージ受信モードとして **Stream 常時接続**（推奨）または **HTTP コールバック / Outgoing** を選択できます。DingTalk のカスタムグループボット Webhook はコマンドを受信できません。

#### QR コードで追加（推奨）

1. システムの「コマンドボット」ページで **DingTalk QR コードで追加** をクリックします。
2. スマートフォンの DingTalk で QR コードを読み取り、組織を選択してページの指示に従いボット情報を入力し、作成を確認します。
3. システムは Client ID / Client Secret を自動取得し、Client ID を Robot Code として Stream 常時接続を有効にします。QR コードの有効期限は 10 分です。
4. 作成後は DingTalk でボットを検索して 1 対 1 チャットを開始するか、グループチャットに追加できます。読み取った人の `staffId` は識別のみに使用され、利用メンバーは引き続き Web 認可または許可リストへの追加が必要です。

> 同じプラットフォームに有効なボットが既にある場合、またはボットのクォータが上限に達している場合、QR コードは拒否されます。先にページで古いボットを処理してください。
>
> QR コードでは DingTalk 公式のアプリ登録ページを使用します。組織が QR コード作成を制限している場合や、登録ページが異常を返す場合も、下記の手動設定を利用できます。

#### 手動設定

1. [DingTalk 開発者プラットフォーム](https://open.dingtalk.com/)を開き、企業内アプリを作成します。
2. 「アプリ機能を追加」で **ボット** を追加します。
3. メッセージ受信モードを選択します：
   - **Stream モード（推奨）**：ボット設定で Stream モードを選択して公開します。公開コールバックアドレスは不要です。
   - **HTTP コールバック / Outgoing**：システムに表示される `/webhooks/dingtalk/<slug>` アドレスを入力し、署名検証用の App Secret を入力します。
4. システムで「DingTalk ボット」を作成し、Client ID（App Key）と Client Secret（App Secret）を入力して、同じ受信モードを選択します。
5. イベント通知をプッシュする場合は、Robot Code（通常は Client ID と同じ）を入力し、アプリにボットからの能動的なメッセージ送信権限があることを確認します。
6. アプリを公開し、ボットをグループチャットに追加して `/help` を送信します。

#### システム側のフィールド

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| 名前 | はい | システム内での識別のみに使用 |
| メッセージ受信モード | はい | HTTP コールバック / Stream 常時接続。QR コード作成では既定で Stream |
| App Key（Client ID） | Stream では必須 | DingTalk アプリの Client ID。イベント通知にも必要 |
| App Secret（Client Secret） | Stream では必須 / HTTP では署名検証 | Stream の接続認証情報。HTTP コールバックではコールバック署名の検証に使用 |
| Robot Code | イベント通知では推奨 | ボットコード。通常は Client ID と同じ |
| 所有者プラットフォームユーザー ID | 入力推奨 | DingTalk の `staffId` を入力 |
| API Base URL | いいえ | テスト / プロキシ専用。本番環境では空欄 |

#### メッセージ受信と返信の説明

- **Stream モード**：サーバーは Client ID / Secret を使用して DingTalk Stream ゲートウェイに能動的に接続するため、公開 IP、ドメイン、コールバックアドレスは不要です。ボットのメッセージは常時接続でプッシュされ、システムは直ちに ACK を返してからコマンドを非同期に実行します。
- **HTTP コールバック**：DingTalk のコールバックリクエストヘッダーには `timestamp`（ミリ秒）と `sign` が含まれます。システムは App Secret をキーとして `timestamp + "\n" + App Secret` の HMAC-SHA256 を計算し、±1 時間のずれを許容します。
- どちらのモードも `msgtype = text` のテキストメッセージのみを処理します。
- ユーザー ID は `senderStaffId` を優先し、次に `senderId` を使用します。所有者 ID と許可リストには `staffId` を入力してください。
- 返信はメッセージボディ内の `sessionWebhook` を使用して markdown を送信し、コマンド送信者を @ メンションします。この Webhook は通常約 1.5 時間有効です。期限切れ後はコマンドを再送信してください。
- システムは DingTalk の `msgId` で重複排除します。Stream モードではさらに配信を直ちに確認し、プラットフォームによる重複配信を防ぎます。

#### 所有者 ID と許可リスト

- コールバックイベント内の `senderStaffId`（次に `senderId`）を基準にします。開発者プラットフォームのイベントデバッグログで確認するか、連絡先のメンバー詳細で照合できます。
- 「所有者 ID」は識別のみに使用され、コマンド権限は自動的に付与されません。すべての DingTalk ユーザーは Web 認可または許可リストへの追加が必要です。
- QR コード作成では読み取った人の `staffId` が返らないことがあるため、手動で補完できます。初回利用時は、ボットの所有アカウントが Web ページにログインして承認すれば利用できます。

### 3.4 WeCom スマートボット（常時接続）

WeCom では**スマートボット**を作成し、**API モード → 常時接続** を選択する必要があります。WeCom のグループボット Webhook は送信のみ可能で、コマンドは受信できません。

> アップグレードの注意：旧版 WeCom 自社開発アプリのコールバック（Token / EncodingAESKey / CorpID / AgentID）はコマンドボットでは使用されなくなりました。既存のボットは「コマンドボット」でスマートボットの Bot ID / Secret を入力して保存し直す必要があります。

#### QR コードで追加（推奨）

1. システムの「コマンドボット」ページで **WeCom QR コードで追加** をクリックします。
2. スマートボットの作成権限がある WeCom で QR コードを読み取り、ページの指示に従ってボットを作成し認可します。
3. システムは Bot ID / Secret を自動取得し、ボットを作成して常時接続を確立します。QR コードの有効期限は 5 分です。
4. 作成後、利用メンバーにコマンドを送信してもらい、ボットの所有アカウントが Web ページにログインして承認します。所有者 UserID は識別のみに使用され、権限は自動的に付与されません。

> 同じプラットフォームに有効なボットが既にある場合、またはボットのクォータが上限に達している場合、QR コードは拒否されます。先にページで古いボットを処理してください。
>
> QR コードでは WeCom 公式の認可ページを使用します。アカウントにスマートボットの作成権限がない場合や、WeCom がページのフローを変更した場合も、下記の手動設定を利用できます。

#### 手動設定

1. [WeCom 管理コンソール](https://work.weixin.qq.com/)または WeCom クライアントのワークベンチを開き、「スマートボット」→ ボットを作成 に進みます。
2. 作成フローで「API モードで作成」→「常時接続を使用」を選択します。
3. **Bot ID** と **Secret** を取得して保存します。Secret は通常 1 回しか表示されず、紛失した場合は再生成できます。
4. システムで「WeCom スマートボット（常時接続）」を作成し、Bot ID、Secret、所有者 UserID を入力します。
5. ボットをグループチャットまたは 1 対 1 チャットに追加します。グループチャットでは **ボットを @ メンション** して `/help` を送信します。
6. コールバックアドレス、Token、EncodingAESKey、CorpID の入力は不要です。サービスが能動的に `wss://openws.work.weixin.qq.com` に接続します。

#### システム側のフィールド

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| 名前 | はい | システム内での識別のみに使用 |
| Bot ID | はい | スマートボットの一意の識別子 |
| Secret | はい | 常時接続専用の Secret。`aibot_subscribe` の認証に使用 |
| 所有者プラットフォームユーザー ID | 入力推奨 | WeCom 連絡先のメンバー UserID。実際のボットコールバックの `from.userid` を基準にします |

#### 常時接続の仕組み

- サーバーは能動的に `wss://openws.work.weixin.qq.com` に接続するため、内部ネットワークのデプロイに適しており、固定の公開 IP は不要です。
- 接続確立後に `aibot_subscribe` を送信し、Bot ID + Secret で本人認証を行います。その後は 30 秒ごとに `ping` ハートビートを送信します。
- ユーザーメッセージは `aibot_msg_callback` で平文プッシュされるため、復号は不要です。システムは `msgtype = text` のみを処理します。
- 返信は `aibot_respond_msg` にコールバック内の `req_id` を付けて markdown を送信します。同じ `req_id` への返信は直列に送信されます。
- 1 つのスマートボットに対して同時に 1 つの有効な常時接続のみが許可されます。新しい接続は古い接続を切断し、複数インスタンスでデプロイすると互いに中断されます。
- 切断時は指数バックオフで再接続します。認証の連続失敗、または接続が新しいインスタンスに置き換えられた場合、ボットのカードに常時接続の異常が表示されます。
- グループチャットのメッセージは、先頭の `@ボット` を除去してからスラッシュコマンドとして解析します。
- メッセージのコールバック後 24 時間以内であれば返信できます。システムはバックグラウンドキューでコマンドを実行するため、長いコマンドは通常数秒かかります。
- ボットのイベント通知を有効にすると、システムは同じ常時接続で `aibot_send_msg` を使用し、最近の会話に能動的にプッシュします。ユーザーが事前にボットへメッセージを送信している必要があります。

#### 所有者 ID と許可リスト

- WeCom 連絡先の **UserID**（メンバーアカウント）を入力してください。氏名、電話番号、外部連絡先 ID は入力しないでください。
- ボットの作成者が企業のスーパー管理者でない場合、`from.userid` は企業主体配下の暗号化された userid になることがあります。所有者と許可リストは、実際のコールバックイベント内の値を基準に設定してください。

#### 未承認と Web 認可

- WeCom ユーザーが許可リストにない場合、ボットはワンタイムの Web 認可リンク（`PUBLIC_BASE_URL/authorize/<token>`）を返信します。有効期限は 30 分です。
- ボットの所有者は自分の Web アカウントでリンク先のページにログインし、プラットフォームユーザー ID（および利用可能な場合はニックネーム、会話）を確認したうえで、`viewer` または `admin` を選択して承認または拒否します。
- ボットの所有者以外がログインした場合はリクエストを閲覧するだけで、自分で承認することはできません。リンクをボットの所有者に転送する必要があります。
- 認可リンクは 1 回処理すると無効になります。同じユーザーの他の未処理リンクも同期的に更新されます。期限切れ後は、ユーザーに任意のコマンドを再送信してもらい、新しいリンクを生成してください。
- すべての利用メンバー（QR コードを読み取った本人を含む）は、Web 認可または許可リストによって権限を取得する必要があります。自分にすべてのコマンド権限を与えたい場合は、承認時に `admin` を選択してください。
- `PUBLIC_BASE_URL` はブラウザからアクセス可能である必要があります。リンクが開けない場合は、リバースプロキシとこの環境変数を確認してください。

#### 接続状態

ボットのカードには常時接続の状態が表示されます：

- **常時接続中**：接続を確立中、または自動再接続中です。
- **常時接続済み**：認証に成功し、コマンドを受信できます。
- **常時接続異常**：認証情報の誤り、Bot ID / Secret の未入力、ネットワーク到達不可、認証失敗、または接続が他のインスタンスに置き換えられています。
- **常時接続無効**：ボットが無効化されています。

状態が異常のまま続く場合は、Bot ID / Secret、サーバーのアウトバウンドファイアウォールで `wss://openws.work.weixin.qq.com:443` が許可されているか、同じ Bot ID を使用している他のインスタンスがないかを確認してください。

### 3.5 ボットのイベント通知

「コマンドボット」の編集ページで **イベント通知を受信** を選択すると、ボットは発売、セール、削除などのイベントを追加で受信します。通知チャネルとは 2 つの独立した設定であり、同時に有効にできます。

- **通知先**：ボットが最後に許可リストのメンバーに使用された会話です。システムは承認済みユーザーがコマンドの送信に成功した後でのみこの通知先を更新します。未承認ユーザーは通知先を変更しません。
- **前提条件**：対象のボットが、承認済みユーザーから少なくとも 1 回コマンドを受信している必要があります。そうでない場合、イベントは配信されません。ボットのカードには「直近の会話がまだ記録されていません」と表示されます。
- **イベント範囲**：チェック異常を含むすべてのイベントを受信します。ボットごとにイベントタイプを個別に絞り込むことはできません。
- **通知チャネルのグループボットは、引き続き通知チャネル自身のイベント選択ルールに従って送信されます。両者は互いに影響しません。**

各プラットフォームの追加要件：

- **Feishu / Lark**：App ID / App Secret が必要で、アプリとして会話にメッセージを送信する権限が必要です。イベントは最近の会話の `chat_id` に送信されます。HTTP コールバックと常時接続のどちらのモードでも可能です。
- **DingTalk**：App Key、App Secret、Robot Code が必要で、ボットからの能動的なメッセージ送信権限が必要です。グループチャットでは `openConversationId`、1 対 1 チャットでは送信者の `staffId` を使用します。
- **WeCom**：常時接続の `aibot_send_msg` で最近の会話にプッシュします。1 対 1 チャットは `chat_type=1`、グループチャットは `chat_type=2` です。ユーザーは事前にボットと会話している必要があります。

> ボットが無効化された、イベント通知スイッチがオフになった、最近の会話が削除された、またはボットがグループチャットから削除された場合、配信はキャンセルまたは失敗します。承認済みユーザーにコマンドを 1 回送信してもらえば、対象の会話を更新できます。

## 4. コマンド早見表

```text
/help
/add <appid | ストアリンク | 名前> [--discount N] [--note テキスト] [--force]
/adddlc <ベースゲームの appid | リンク | 名前> [--max 50]
/remove <id | appid | 名前>
/pause <id | appid | 名前>
/resume <id | appid | 名前>
/check <id | appid | 名前>
/price <id | appid | 名前>
/list [--all] [--sale] [--paused] [--page N]
/events [--item id] [--limit 10]
/cancel
```

説明：

- `/add` は Steam ストアの直接検索に対応しています。名前検索で複数の結果が返った場合は、番号を返信して選択します。
- `--discount N` は割引通知のしきい値（0〜100）を設定します。未指定の場合はアカウントの既定値を使用します。
- `--force` は、現在のリージョンで取得できないものの、追加してニュースの事前警告のみを行いたい場合に使用します。
- `/adddlc` はベースゲームのすべての DLC をインポートし、1 回あたり最大 50 個です。
- `/check` はキャッシュを迂回して直ちにチェックし、イベントを書き込みます。Steam のレート制限の影響を受けます。
- `/list` は既定で一時停止中の項目を表示しません。`--all` で全件、`--sale` でセール中の項目のみ、`--paused` で一時停止中の項目のみを表示します。
- `/events` は既定で直近 10 件を表示し、最大 20 件です。
- 閲覧者権限では `/help`、`/list`、`/price`、`/events` のみ使用できます。

## 5. よくある問題のトラブルシューティング

| 現象 | 考えられる原因 | 対処 |
| --- | --- | --- |
| Feishu / Lark / DingTalk でコールバックアドレスの保存に失敗する | サービスがインターネットからアクセスできない、証明書が無効、`PUBLIC_BASE_URL` が誤っている | モバイル通信でコールバックドメインにアクセスする。HTTPS 証明書チェーンが完全であることを確認する。ボットが作成済みで有効になっていることを確認する |
| Feishu / Lark / DingTalk のコールバックが 404 を返す | ボットが無効化・削除された、または `<slug>` が誤っている | 「コマンドボット」ページで最新のコールバックアドレスをコピーする。ボットを有効にする |
| Feishu / Lark でチャレンジ検証の失敗 / 401 が発生する | Verification Token または Encrypt Key が一致しない。プロキシがリクエストボディを書き換えている | 両側を再確認する。リクエストボディの圧縮 / 書き換えを無効にする。`X-Lark-*` ヘッダーを保持する |
| Feishu / Lark で暗号化を有効にするとボットが応答しない | プラットフォームで Encrypt Key を有効にしたがシステム側に入力がなく、暗号文を解析できない。Verification Token の検証により直接 401 が返る可能性もある | システムに同じ Encrypt Key と Verification Token を入力する。またはプラットフォームの暗号化を無効にして再保存する |
| Feishu / Lark でメッセージは受信できるが返信できない | App ID / App Secret が未入力、またはメッセージ送信権限がない | 認証情報を補完する。開発者プラットフォームでメッセージ送信権限を申請して公開する |
| Feishu / Lark の常時接続が接続中 / 異常のままになる | App ID / App Secret が誤っている。アプリで「常時接続でイベントを受信」が有効になっていない。企業が QR コード作成を制限している | 認証情報を確認する。イベントとコールバックで常時接続に切り替えてバージョンを公開する。または HTTP コールバックに変更する |
| QR コード読み取り後に Feishu / Lark ボットが検索できない | アプリが未公開、または利用範囲に対象メンバーが含まれていない | 開発者プラットフォームでバージョンを作成して公開し、利用範囲を調整する。アプリ名で検索する |
| Feishu の QR コードを読み取ったが Lark アプリが作成された | 読み取ったアカウントが Lark テナントに属しており、システムが認可ドメインを自動的に切り替えた | 正常な動作です。Lark でアプリ名を検索してください |
| DingTalk のコールバックが 401 を返す | App Secret が誤っている。リクエストヘッダーがプロキシで削除された。サーバー時刻のずれが 1 時間を超えている | アプリの App Secret（「加签」キーではない）を確認する。`timestamp`、`sign` を保持する。NTP を同期する |
| DingTalk の返信がタイムアウト / 失敗する | `sessionWebhook` の有効期限が切れている | コマンドを再送信する。コールバックが数秒以内に完了することを確認する |
| DingTalk Stream が接続されない / 異常のまま | Client ID / Secret が誤っている。ボットで Stream モードが選択されていない。アプリが未公開。サーバーが `api.dingtalk.com` へアウトバウンドアクセスできない | 認証情報を確認する。ボット設定で Stream を選択してバージョンを公開する。アウトバウンドネットワークを確認する |
| DingTalk の QR コードで認可失敗と表示される | 読み取ったアカウントに開発者権限がない。QR コードの有効期限が切れている。選択した企業がアプリ作成を許可していない。認可ページのテンプレート読み込みに失敗した | アカウントが対象企業で開発者権限を持つことを確認する。QR コードを再生成する。権限のある企業に切り替える。それでも失敗する場合は、サービスログの `钉钉扫码授权失败` の理由を確認する |
| DingTalk の QR コード読み取り後にボットが返信しない | アプリが未公開、または利用範囲に対象メンバーが含まれていない。ボットが会話に追加されていない。Stream 接続が確立されていない | アプリを公開して利用範囲を調整する。ボットのカードで接続状態を確認する。コマンドを再送信する |
| DingTalk / Feishu のユーザーに未承認と表示される | そのプラットフォームのユーザーが許可リストになく、Web 認可も完了していない | ユーザーに任意のコマンドを送信させて認可リンクを取得し、ボットの所有アカウントで Web ページにログインして承認する。または許可リストに直接追加する |
| WeCom の常時接続が未接続 / 異常 | Bot ID または Secret が誤っている。サーバーが `openws.work.weixin.qq.com:443` へアウトバウンドアクセスできない。別のインスタンスが同じボットを使用している。ボットが無効化されている | Bot ID / Secret を確認する。アウトバウンドのファイアウォールとプロキシを確認する。重複デプロイがないことを確認する。ボットのカードで状態とエラーメッセージを確認する |
| WeCom のメッセージに返信がない | 常時接続が切断されている。メッセージが 24 時間の返信ウィンドウを超えている。処理中にボットが無効化または削除された | 常時接続の状態を確認する。コマンドを再送信する。ボットが有効なままであることを確認する |
| WeCom で接続が置き換えられたと表示される | 同じ Bot ID で新しい接続が確立され、古い接続が WeCom 側で切断された | 各ボットにつき実行インスタンスを 1 つだけにする。重複デプロイのサービスを停止するか、システムで無効化してから再度有効にする |
| コマンドに応答がない | グループチャットでボットを @ メンションしていない。メッセージがテキストでない。`/` で始まっていない。ユーザーが許可リストにない | グループでボットを @ メンションする。`/help` を送信する。プラットフォームのユーザー ID を許可リストに追加する |
| QR コードを読み取った本人にもコマンド権限がない | 所有者 ID は識別のみに使用され、権限を暗黙に付与しない | Web 認可ページで自分のプラットフォームアカウントを承認する。またはボットの所有アカウントに自分のプラットフォーム ID を許可リストへ追加してもらう |
| ボット作成が競合する | 同じプラットフォームに有効なボットが既に存在する | 先に古いボットを無効化してから、新しいボットを有効にする |
| 通知チャネルのテストに失敗する | Webhook が無効、署名シークレットが誤っている、キーワード / IP ホワイトリストの制限 | Webhook を再コピーする。署名シークレットを確認する。プラットフォームのセキュリティ設定を確認する |
| グループにイベント通知が届かない | チャネルが無効、イベントタイプが未選択、グループボットが削除された | チャネルの状態とイベント購読を確認する。テストメッセージを再送信する |
| ボットがイベント通知をプッシュしない | 「イベント通知を受信」が無効。直近の承認済み会話がない。DingTalk で App Key / Robot Code が不足。ボットが無効化されている | ボットを編集して通知を有効にする。承認済みユーザーに先にコマンドを 1 回送信してもらう。DingTalk の認証情報を補完する。配信記録を確認する |
| Feishu / Lark / DingTalk が同じメッセージを重複してプッシュする | プラットフォームが ACK を時間内に受信できない、またはネットワークの揺らぎ | システムはメッセージ ID で重複排除します。コールバックが 10 秒以内に返ることを確認する |

### デバッグのヒント

1. まずシステムの「コマンドボット」カードにある **コマンドシミュレーション** を使用し、ボット所有者としてローカルに実行して、コマンドのロジックとクォータが正常であることを確認します。
2. 次に「通知チャネル」の **テスト送信** で Webhook と署名を検証します。
3. 最後にプラットフォームのチャットで `/help` を送信し、コールバック / 常時接続、権限、返信の経路を確認します。
4. コンテナログを確認します：`docker compose logs -f steam-monitor`。`wecom`、`webhook`、`inbound`、`delivery` 関連のログに注目してください。

## 6. セキュリティの推奨事項

- Feishu / Lark / DingTalk のコールバックアドレス、グループボット Webhook、WeCom の Bot ID / Secret はすべて認証情報とみなし、公開リポジトリへのコミットや公開グループへの投稿は行わないでください。
- Feishu / Lark の HTTP コールバックでは Encrypt Key + Verification Token を有効にすることを推奨します。常時接続の認証情報も同様に秘匿する必要があります。DingTalk の HTTP コールバックでは App Secret を入力して署名検証を行う必要があり、Stream モードでも Client Secret を保護してください。WeCom では Bot ID と常時接続の Secret を必ず保護してください。
- 許可リストは最小権限の原則に従ってください。一般メンバーには `viewer`、管理者のみに `admin` を使用します。
- SQLite ファイルをインターネットに公開しないでください。データベースを定期的にバックアップし、`.env` の `APP_SECRET` も併せてバックアップしてください。
- `PUBLIC_BASE_URL` を変更したりドメインを変更したりした後は、Feishu / Lark / DingTalk の管理画面のコールバックアドレスを速やかに更新してください。常時接続モードは影響を受けません。
- 認証情報の漏洩が疑われる場合は、Feishu / Lark では App Secret / Encrypt Key をリセットし、DingTalk では Client Secret をリセットし、WeCom ではスマートボットの Secret を再生成して、システム側でも再入力してください。
