# Руководство по подключению Feishu / Lark, DingTalk и WeCom

[简体中文](BOT_INTEGRATION.md) | [繁體中文](BOT_INTEGRATION.zh-TW.md) | [English](BOT_INTEGRATION.en.md) | [Deutsch](BOT_INTEGRATION.de.md) | [Français](BOT_INTEGRATION.fr.md) | [Italiano](BOT_INTEGRATION.it.md) | [日本語](BOT_INTEGRATION.ja.md) | [한국어](BOT_INTEGRATION.ko.md) | [조선어](BOT_INTEGRATION.ko-KP.md) | [Nederlands](BOT_INTEGRATION.nl.md) | [Русский](BOT_INTEGRATION.ru.md)

[← Назад к README](../README.ru.md)

В этой статье описано, как подключить Feishu / Lark, DingTalk и WeCom к Steam Games Monitor. В проекте есть две разные возможности, которые не заменяют друг друга; сначала определите цель:

| Цель | Что создать на стороне платформы | Точка входа в системе | Направление |
| ----------------------------------- | ---------------------------------------------------------------------------------------- | -------------- | ------------------------ |
| Получение уведомлений о релизах, распродажах, снятии с продажи | Пользовательский бот группы / Webhook группового бота | **Каналы уведомлений** | Одностороннее: система → группа |
| Отправка команд `/add`, `/list` и других в чате | Корпоративное собственное приложение Feishu / Lark / внутренний корпоративный бот DingTalk (Outgoing) / интеллектуальный бот WeCom (постоянное соединение) | **Боты команд** | Двустороннее: платформа → система → платформа |

> Webhook группового бота обычно умеет только отправлять сообщения и не принимает команды. В Feishu / Lark и DingTalk приложение можно создать одним сканированием QR-кода и выбрать HTTP-колбэк или постоянное соединение; в WeCom необходимо создать интеллектуального бота и использовать постоянное соединение.
>
> Каналы уведомлений и боты команд — две независимые конфигурации: для одной платформы можно настроить только уведомления, только команды или и то, и другое.

## 1. Общая подготовка

### 1.1 Публичный HTTPS и PUBLIC_BASE_URL (режим HTTP-колбэка)

Для Feishu / Lark / DingTalk с **HTTP-колбэком** платформа должна сама отправлять сообщения на ваш сервер, поэтому необходимо:

- Сервис должен быть доступен из интернета по адресу **HTTPS**, принимаемому платформой.
- `PUBLIC_BASE_URL` в `.env` должен совпадать с фактическим адресом, по которому обращается браузер, например `https://steam.example.com`.
- Не используйте значение по умолчанию `http://localhost:8787`, иначе платформа не сможет обратиться к сгенерированному адресу колбэка.
- Рекомендуется использовать отдельный домен или поддомен. Путь колбэка фиксирован — `/webhooks/...`; не развёртывайте сервис по вложенному пути, требующему дополнительного переписывания.

Отображаемые в системе адреса колбэков формируются по следующим правилам:

```text
Feishu / Lark  https://<домен PUBLIC_BASE_URL>/webhooks/feishu/<slug>
DingTalk       https://<домен PUBLIC_BASE_URL>/webhooks/dingtalk/<slug>
```

`<slug>` генерируется случайно при создании бота и уникален для каждого бота. После изменения `PUBLIC_BASE_URL` адреса колбэков меняются, их необходимо своевременно обновить в административной консоли платформы.

> **Режим постоянного соединения** Feishu / Lark, **режим Stream** DingTalk и интеллектуальный бот WeCom устанавливают исходящее соединение со стороны сервера и не требуют публичного адреса колбэка, публичного IP, Token или EncodingAESKey. Созданные по QR-коду приложения Feishu / Lark и боты DingTalk по умолчанию используют постоянное соединение.
>
> Однако `PUBLIC_BASE_URL` по-прежнему должен открываться в браузере владельца бота: по этому адресу формируются ссылки веб-авторизации, которые получают неавторизованные пользователи.

### 1.2 Требования к обратному прокси

Nginx, Caddy, Traefik или облачный балансировщик нагрузки должны обеспечивать следующее (это касается только HTTP-колбэков Feishu / Lark / DingTalk):

- **Передавать тело запроса без изменений**: не сериализуйте JSON заново, не сжимайте и не изменяйте содержимое — подписи Feishu / Lark и DingTalk вычисляются по исходному телу запроса.
- Сохраняйте заголовки платформы: `X-Lark-Request-Timestamp`, `X-Lark-Request-Nonce`, `X-Lark-Signature` в Feishu и `timestamp`, `sign` в DingTalk.
- Сохраняйте параметры запроса, не теряйте параметры подписи.
- Не добавляйте для `/webhooks/*` аутентификацию, Basic Auth, HTML-редиректы или интерактивную проверку WAF.
- Максимальный размер тела запроса — не менее 1 MB; тайм-аут чтения — не менее 10 секунд.
- Используйте доверенный TLS-сертификат: платформа проверяет цепочку сертификатов.

Постоянные соединения Feishu / Lark, DingTalk Stream и WeCom не проходят через обратный прокси — достаточно, чтобы сервер мог исходящим соединением обратиться к соответствующей платформе (Lark использует `open.larksuite.com`, DingTalk Stream — `api.dingtalk.com`).

### 1.3 Синхронизация времени и ключи

- На сервере должна быть включена синхронизация времени по NTP. Подпись Feishu / Lark допускает отклонение ±300 секунд, колбэк DingTalk Outgoing — ±1 час.
- `APP_SECRET` (не менее 32 символов) используется для шифрованного хранения учётных данных каналов и ботов. **Не меняйте его без необходимости и не теряйте**: после смены сохранённые App Secret, Secret ботов, Encrypt Key и т. п. расшифровать не удастся — их придётся ввести заново.
- Учётные данные ботов хранятся в SQLite в зашифрованном виде (AES-256-GCM); API и веб-интерфейс не показывают открытый текст, а пустое поле при редактировании означает сохранение прежнего значения.

### 1.4 Рекомендуемый порядок создания

Feishu / Lark (по QR-коду, рекомендуется):

1. В разделе «Боты команд» нажмите «QR-код Feishu / Lark», выберите Feishu или международную версию Lark и отсканируйте код.
2. На странице платформы создайте приложение и подтвердите; система автоматически запишет App ID / App Secret, `open_id` владельца и включит постоянное соединение.
3. Найдите приложение по названию в Feishu / Lark и начните личный чат или добавьте бота в групповой чат.
4. Отправьте `/help`, чтобы проверить работу команд и ответов.

Feishu / Lark (вручную):

1. Создайте бота в системе, выберите версию (Feishu / Lark) и способ получения событий (HTTP-колбэк / постоянное соединение).
2. HTTP-колбэк: скопируйте адрес колбэка в административную консоль платформы и настройте Encrypt Key / Verification Token; постоянное соединение: выберите на платформе «Получать события через постоянное соединение».
3. Подпишитесь на `im.message.receive_v1`, запросите права на чтение и отправку сообщений.
4. Опубликуйте приложение, добавьте бота в группу или настройте область видимости.
5. Отправьте `/help` для проверки.

DingTalk (по QR-коду, рекомендуется):

1. В разделе «Боты команд» нажмите «Добавить DingTalk по QR-коду», отсканируйте код мобильным DingTalk и подтвердите создание.
2. Система автоматически запишет Client ID / Client Secret, использует Client ID как Robot Code и включит постоянное соединение Stream.
3. Найдите бота в DingTalk и начните личный чат или добавьте его в групповой чат.
4. Отправьте `/help` для проверки.

DingTalk (вручную):

1. Создайте бота в системе, выберите режим получения сообщений и скопируйте адрес колбэка (для режима HTTP).
2. В административной консоли платформы создайте приложение / бота, укажите адрес колбэка и ключ либо выберите режим Stream в настройках бота.
3. При сохранении колбэка платформа обычно выполняет проверку URL; убедитесь, что система запущена и бот включён.
4. Опубликуйте приложение на платформе, добавьте бота в группу или настройте область видимости.
5. Отправьте `/help`, чтобы проверить работу команд и ответов.

WeCom:

1. В административной консоли WeCom создайте интеллектуального бота, выберите режим API → постоянное соединение и получите Bot ID и Secret.
2. В системе создайте «Интеллектуальный бот WeCom (постоянное соединение)», укажите Bot ID, Secret и UserID владельца.
3. После сохранения система автоматически установит постоянное соединение; проверка URL на платформе не требуется.
4. Добавьте бота в групповой или личный чат и отправьте `/help` для проверки.

## 2. Каналы уведомлений (односторонняя отправка)

Каналы уведомлений предназначены для отправки событий мониторинга в групповые чаты; публичный адрес колбэка не нужен — достаточно URL Webhook, предоставленного платформой.

### 2.1 Сравнение трёх типов групповых ботов

| Платформа | Тип в системе | Формат сообщения | Подпись | Описание |
| -------- | -------------------------- | -------- | ------------ | ---------------------------------------------- |
| WeCom | Групповой бот WeCom | markdown | Нет | Около 4096 байт на сообщение, система обрезает текст; групповой бот умеет только отправлять |
| Feishu | Бот Feishu (пользовательский бот) | Интерактивная карточка | Необязательный ключ подписи | Можно включить проверку подписи; рекомендуется включить |
| DingTalk | Бот DingTalk (пользовательский бот) | markdown | Необязательный секрет подписи | Можно включить подпись; система вычисляет её по правилам DingTalk |

Точка входа: в левом меню **Каналы уведомлений → Новый канал**. Укажите название, Webhook, при необходимости ключ подписи и отметьте события для подписки.

> По умолчанию уведомления о событиях отправляются через Webhook группового бота, настроенный здесь; «Боты команд» также могут отдельно включить уведомления о событиях — эти механизмы независимы и могут использоваться одновременно.

### 2.2 Групповой бот WeCom

1. Откройте групповой чат WeCom → настройки группы → групповые роботы → добавить робота.
2. Скопируйте адрес Webhook (обычно вида `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...`).
3. В системе в разделе «Каналы уведомлений» выберите **Групповой бот WeCom**, вставьте Webhook и сохраните.
4. Нажмите «Отправить тест» на карточке канала и убедитесь, что сообщение пришло в группу.

Примечания:

- Сам Webhook является учётными данными: при утечке любой сможет отправлять сообщения в группу. В этом случае удалите бота в группе и добавьте заново.
- Групповой бот не принимает команды вроде `/add`; для команд используйте «Интеллектуальный бот WeCom (постоянное соединение)».
- Ограничение на одно сообщение — около 4096 байт; система обрезает текст, поэтому длинные списки могут отображаться не полностью.
- Для групповых ботов действуют ограничения частоты; при срабатывании лимита система автоматически повторяет попытку.

### 2.3 Пользовательский бот Feishu

1. Откройте группу Feishu → настройки группы → групповые роботы → добавить робота → пользовательский робот.
2. Скопируйте адрес Webhook (обычно вида `https://open.feishu.cn/open-apis/bot/v2/hook/...`).
3. Рекомендуется выбрать в настройках безопасности **проверку подписи** и скопировать ключ подписи.
4. В системе в разделе «Каналы уведомлений» выберите **Бот Feishu**, вставьте Webhook; если включена подпись, укажите ключ подписи.
5. После сохранения отправьте тестовое сообщение.

Правила подписи (реализованы в системе, вычислять вручную не нужно):

- Временная метка — в секундах.
- В качестве ключа HMAC-SHA256 используется `timestamp + "\n" + secret`, подпись вычисляется для пустой строки и кодируется в Base64.
- Временная метка и подпись отправляются вместе с телом сообщения.

Если вместо подписи используются «пользовательские ключевые слова» или «белый список IP», убедитесь, что текст уведомления содержит ключевое слово, либо добавьте исходящий IP сервера в белый список.

### 2.4 Пользовательский бот DingTalk

1. Откройте группу DingTalk → настройки группы → умный групповой помощник → добавить робота → пользовательский.
2. Скопируйте адрес Webhook (обычно вида `https://oapi.dingtalk.com/robot/send?access_token=...`).
3. Рекомендуется выбрать в настройках безопасности **подпись** и скопировать секрет подписи.
4. В системе в разделе «Каналы уведомлений» выберите **Бот DingTalk**, вставьте Webhook; если включена подпись, укажите секрет подписи.
5. После сохранения отправьте тестовое сообщение.

Правила подписи (реализованы в системе):

- Временная метка — в миллисекундах.
- С ключом `secret` вычисляется HMAC-SHA256 для `timestamp + "\n" + secret`, результат кодируется в Base64.
- `timestamp` и `sign` передаются как параметры URL.

Если вместо подписи используются «пользовательские ключевые слова» или «диапазоны IP», настройте параметры безопасности соответствующим образом. При срабатывании лимита (например, код ошибки `90037`) система автоматически повторяет попытку.

### 2.5 Подписка на события и повторные попытки

В канале уведомлений можно выбрать типы событий для подписки:

| Событие | Описание |
| ------------------- | ---------------------------------------------- |
| `release` | Официальный релиз игры / DLC |
| `release_date` | Получена точная дата выхода или дата выхода изменилась |
| `sale_start` | Скидка достигла порога мониторинга |
| `sale_change` | Изменение размера скидки или цены во время распродажи |
| `sale_end` | Окончание скидки, возврат к базовой цене |
| `price_change` | Изменение базовой цены вне распродажи или изменение статуса «бесплатно» |
| `delisting_warning` | Совпадение ключевых слов снятия с продажи в новостях Steam (эвристика, требуется ручное подтверждение) |
| `delisted` | Два последовательных подтверждения недоступности покупки в магазине |
| `restored` | Восстановление возможности покупки |
| `check_error` | Ошибка проверки |

- Если **не отмечено ни одного события**, по умолчанию принимаются все события, кроме `check_error`.
- При неудачной отправке повторные попытки выполняются через 30 секунд → 2 минуты → 10 минут → 1 час → 6 часов → 24 часа, максимум 6 раз.
- На карточке каждого канала есть кнопка «Отправить тест» для проверки Webhook и настроек подписи.

## 3. Боты команд (двусторонняя связь)

Боты команд позволяют пользователям управлять объектами мониторинга с помощью слэш-команд в чатах Feishu / Lark, DingTalk или WeCom. Feishu / Lark поддерживают HTTP-колбэк или постоянное WebSocket-соединение, DingTalk — HTTP-колбэк или постоянное соединение Stream, WeCom — постоянное WebSocket-соединение; результаты возвращаются в исходный сеанс через API платформы или постоянное соединение.

### 3.1 Общее поведение

- **Область действия**: команды всегда применяются к данным учётной записи, которой принадлежит бот. Даже если ботом пользуется другой администратор из списка разрешённых, изменяются объекты мониторинга владельца бота.
- **Идентификатор владельца**: `ownerPlatformUserId` служит только для идентификации сканировавшего / владельца бота и не даёт прав на выполнение команд автоматически.
- **Список разрешённых**: любой пользователь платформы (включая ID владельца) должен быть добавлен в список разрешённых, чтобы выполнять команды; роли:
  - `admin`: доступны все команды.
  - `viewer`: доступны только `/help`, `/list`, `/price`, `/events`.
  - Пользователи Feishu / Lark, DingTalk и WeCom, отсутствующие в списке разрешённых, получают одноразовую ссылку веб-авторизации, и бот не выполняет исходную команду; в DingTalk такая ссылка также поддерживается.
- **Уведомления о событиях**: на странице редактирования бота можно отдельно включить «Получать уведомления о событиях», чтобы отправлять события в сеанс, который последним использовал авторизованный пользователь. Эта настройка независима от «Каналов уведомлений» и может быть включена одновременно с ними. При отсутствии последнего сеанса доставка не выполняется; подробнее в разделе 3.5.
- **Формат сообщений**: обрабатываются только текстовые сообщения. Изображения, файлы, форматированный текст и карточки игнорируются.
- **Формат команд**: начинаются с `/` или полноширинного `／`; поддерживаются `/add@бот`, аргументы в кавычках и `--flag=value`.
- **Дедупликация**: при повторной доставке одного и того же сообщения платформой система выполняет дедупликацию по ID события / сообщения платформы и обрабатывает его один раз.
- **Ограничение частоты**: не более 10 команд в минуту от одного пользователя платформы, не более 30 в минуту в одном сеансе и не более 60 в минуту на одного бота; при срабатывании лимита предупреждение выводится не чаще раза в минуту.
- **Асинхронные ответы**: колбэки Feishu / Lark / DingTalk сначала быстро возвращают успех, сообщения DingTalk Stream / WeCom принимаются через постоянное соединение; команды выполняются в фоне, а результаты отправляются через API платформы или постоянное соединение. Отображение ответа на платформе может немного задерживаться.
- **Выбор из нескольких результатов**: если поиск по названию для `/add` и `/adddlc` возвращает несколько результатов, бот отправляет нумерованный список; ответьте номером (действует 10 минут) или отправьте `/cancel` для отмены.
- **Квоты**: в одной учётной записи можно создать не более 3 ботов; на одной платформе может быть только 1 включённый бот (Feishu и международная версия Lark используют общую квоту платформы «Feishu»). У ботов Feishu / Lark / DingTalk с HTTP-колбэком после отключения адрес колбэка сразу перестаёт работать (возвращает 404); у ботов с постоянным соединением / Stream после отключения соединение разрывается.

### 3.2 Приложение-бот Feishu / Lark (рекомендуется)

> #### Почему рекомендуется
>
> Feishu/Lark поддерживает персональную версию, что позволяет удобно разделить личную жизнь и работу.



В Feishu / Lark необходимо создать **корпоративное собственное приложение**, включить возможность бота и подписаться на события сообщений. Webhook пользовательского группового бота не принимает команды. Feishu (китайская версия) использует `open.feishu.cn` / `accounts.feishu.cn`, международная версия Lark — `open.larksuite.com` / `accounts.larksuite.com`; в системе они различаются параметром «Версия» в настройках бота.

#### Создание одним сканированием QR-кода (рекомендуется)

1. В разделе «Боты команд» нажмите **QR-код Feishu / Lark** и в диалоговом окне выберите «Feishu» или «Международная версия Lark».
2. Отсканируйте код соответствующим клиентом; на странице будет предзаполнено название приложения, и разрешено только создание нового приложения.
3. После подтверждения система автоматически получит App ID / App Secret, запишет `open_id` сканировавшего как владельца и включит постоянное соединение.
4. QR-код действителен 10 минут; если на платформе уже есть включённый бот или квота исчерпана, запрос будет отклонён.
5. Найдите приложение по названию в Feishu / Lark и начните личный чат либо добавьте бота в групповой чат и отправьте `/help`.

> При создании по QR-коду используется официальный шаблон Feishu `PersonalAgent` с предварительно настроенными возможностями бота, правами на сообщения и событием `im.message.receive_v1`; способ получения событий — постоянное соединение. Если ваша организация ограничивает создание по QR-коду, используйте ручную настройку ниже.
>
> Если QR-код Feishu будет отсканирован в тенанте Lark, система автоматически переключится на `accounts.larksuite.com` для завершения авторизации.

#### Ручная настройка

1. Откройте [открытую платформу Feishu](https://open.feishu.cn/app) или [открытую платформу Lark](https://open.larksuite.com/app) и создайте корпоративное собственное приложение.
2. В разделе «Добавление возможностей приложения» включите **Бот**.
3. В разделе «Управление правами» запросите права, связанные с сообщениями:
   - `im:message.p2p_msg:readonly`: чтение личных сообщений, отправленных боту пользователем.
   - `im:message.group_at_msg:readonly`: получение сообщений группового чата с упоминанием @ бота.
   - `im:message:send_as_bot`: отправка сообщений от имени приложения.
   - Если в консоли права разделены по сценариям, запросите также права на чтение содержимого сообщений и на отправку сообщений.
4. Создайте в системе «Приложение-бот Feishu / Lark», выберите версию и способ получения событий:
   - **Постоянное соединение (рекомендуется)**: на платформе в разделе «События и колбэки» выберите «Получать события через постоянное соединение» и подпишитесь на `im.message.receive_v1`; адрес колбэка не нужен.
   - **HTTP-колбэк**: укажите в качестве адреса запроса отображаемый в системе `/webhooks/feishu/<slug>`; при необходимости шифрования заполните Encrypt Key и Verification Token.
5. Создайте версию и опубликуйте приложение; в разделе «Доступность приложения» убедитесь, что пользователи могут им пользоваться.
6. Добавьте бота в групповой чат или начните с ним личный чат.

#### Поля на стороне системы

| Поле | Обязательно | Описание |
| ------------------ | ----------------- | ---------------------------------------------------------------- |
| Название | Да | Только для идентификации в системе |
| Версия | Да | Feishu (китайская версия) или Lark (международная) |
| Способ получения событий | Да | HTTP-колбэк / постоянное соединение; при создании по QR-коду по умолчанию постоянное соединение |
| App ID | Желательно указать | Необходим для получения `tenant_access_token`, ответов и отправки событий |
| App Secret | Желательно указать | Используется вместе с App ID |
| Encrypt Key | Зависит от платформы при HTTP-колбэке | Должен полностью совпадать с настройками в консоли Feishu / Lark; обязателен при включённом шифровании |
| Verification Token | Рекомендуется при HTTP-колбэке | Должен совпадать с платформой; используется для проверки источника событий |
| ID пользователя платформы-владельца | Желательно указать | Укажите `open_id` Feishu / Lark (обычно начинается с `ou_`); при создании по QR-коду заполняется автоматически |
| API Base URL | Нет | Только для тестов / прокси; в production оставьте пустым |

#### Колбэки, постоянные соединения и подписи

- **HTTP-колбэк**: при сохранении адреса подписки на события платформа отправляет запрос-проверку `url_verification`, и система возвращает `challenge`.
  - Если задан Encrypt Key, система проверяет подпись заголовков `SHA256(timestamp + nonce + encryptKey + rawBody)` с допустимым отклонением ±300 секунд, затем расшифровывает зашифрованное содержимое.
  - Если задан Verification Token, система проверяет token в событии; при несовпадении возвращается 401.
- **Постоянное соединение**: сервер использует App ID / App Secret для исходящего подключения к эндпоинту постоянного соединения Feishu / Lark; события передаются по аутентифицированному соединению и не требуют проверки подписи, публичного адреса или обратного прокси. Состояние соединения отображается на карточке бота.
- Обрабатываются только текстовые сообщения из `im.message.receive_v1`; сообщения, отправленные самим приложением, игнорируются.
- Для ответа сначала вызывается интерфейс «Ответить на сообщение»; при неудаче выполняется резервная отправка сообщения в `chat_id`.
- В групповом чате команду нужно вводить после **@бот**; в личном чате можно отправлять сразу.

#### ID владельца и список разрешённых

- В событиях Feishu / Lark идентификатором пользователя в первую очередь является `open_id`, поэтому в список разрешённых следует указывать `open_id`, а не номер телефона, адрес электронной почты или имя.
- При создании по QR-коду `open_id` сканировавшего записывается в «ID владельца», но используется только для идентификации и не даёт прав на команды автоматически; при первом использовании всё равно нужно одобрить свою учётную запись платформы через веб-авторизацию.
- При ручной настройке можно посмотреть журнал отладки событий / колбэков либо попросить пользователя отправить сообщение и затем открыть сведения о событии на платформе.

### 3.3 Бот DingTalk (HTTP-колбэк / Stream)

В DingTalk необходимо создать **внутреннего корпоративного бота**; режим получения сообщений — **постоянное соединение Stream** (рекомендуется) или **HTTP-колбэк / Outgoing**. Webhook пользовательского группового бота DingTalk не принимает команды.

#### Добавление по QR-коду (рекомендуется)

1. На странице «Боты команд» нажмите **Добавить DingTalk по QR-коду**.
2. Отсканируйте код мобильным DingTalk, выберите организацию и, следуя подсказкам на странице, заполните данные бота и подтвердите создание.
3. Система автоматически получит Client ID / Client Secret, использует Client ID как Robot Code и включит постоянное соединение Stream; QR-код действителен 10 минут.
4. После успешного создания можно найти бота в DingTalk и начать личный чат или добавить его в групповой чат; `staffId` сканировавшего используется только для идентификации, а участникам всё равно нужна веб-авторизация или добавление в список разрешённых.

> Если на той же платформе уже есть включённый бот или квота исчерпана, сканирование будет отклонено; сначала обработайте старого бота на странице.
>
> Для сканирования используется официальная страница регистрации приложений DingTalk. Если организация ограничивает создание по QR-коду или страница регистрации возвращает ошибку, можно воспользоваться ручной настройкой ниже.

#### Ручная настройка

1. Откройте [открытую платформу DingTalk](https://open.dingtalk.com/) и создайте внутреннее корпоративное приложение.
2. В разделе «Добавление возможностей приложения» добавьте **Бот**.
3. Выберите режим получения сообщений:
   - **Режим Stream (рекомендуется)**: в настройках бота выберите режим Stream и опубликуйте; публичный адрес колбэка не нужен.
   - **HTTP-колбэк / Outgoing**: укажите адрес `/webhooks/dingtalk/<slug>`, отображаемый в системе, и App Secret для проверки подписи.
4. Создайте в системе «Бот DingTalk», укажите Client ID (App Key) и Client Secret (App Secret), выберите тот же режим получения.
5. Для отправки уведомлений о событиях укажите Robot Code (обычно совпадает с Client ID) и убедитесь, что приложение имеет право отправлять сообщения от имени бота.
6. Опубликуйте приложение, добавьте бота в групповой чат и отправьте `/help`.

#### Поля на стороне системы

| Поле | Обязательно | Описание |
| --------------------------- | ----------------------- | ---------------------------------------------- |
| Название | Да | Только для идентификации в системе |
| Режим получения сообщений | Да | HTTP-колбэк / постоянное соединение Stream; при создании по QR-коду по умолчанию Stream |
| App Key (Client ID) | Обязательно для Stream | Client ID приложения DingTalk; также нужен для уведомлений о событиях |
| App Secret (Client Secret) | Обязательно для Stream / проверки HTTP | Учётные данные для подключения Stream; при HTTP-колбэке используется для проверки подписи |
| Robot Code | Рекомендуется для уведомлений о событиях | Код бота; обычно совпадает с Client ID |
| ID пользователя платформы-владельца | Желательно указать | Укажите `staffId` DingTalk |
| API Base URL | Нет | Только для тестов / прокси; в production оставьте пустым |

#### Получение сообщений и ответы

- **Режим Stream**: сервер использует Client ID / Secret для исходящего подключения к шлюзу DingTalk Stream; публичный IP, домен и адрес колбэка не нужны. Сообщения бота передаются по постоянному соединению, система сразу подтверждает их (ACK) и затем асинхронно выполняет команду.
- **HTTP-колбэк**: заголовки запроса DingTalk содержат `timestamp` (в миллисекундах) и `sign`; система с ключом App Secret вычисляет HMAC-SHA256 для `timestamp + "\n" + App Secret` и допускает отклонение ±1 час.
- В обоих режимах обрабатываются только текстовые сообщения с `msgtype = text`.
- Идентификатор пользователя берётся в первую очередь из `senderStaffId`, затем из `senderId`; в ID владельца и список разрешённых следует указывать `staffId`.
- Для ответа используется `sessionWebhook` из тела сообщения: отправляется markdown с упоминанием @ отправителя команды. Такой Webhook обычно действует около 1,5 часа; после истечения срока просто отправьте команду снова.
- Система выполняет дедупликацию по `msgId` DingTalk; в режиме Stream дополнительно сразу подтверждает доставку, чтобы платформа не повторяла отправку.

#### ID владельца и список разрешённых

- Ориентируйтесь на `senderStaffId` (затем `senderId`) в событии колбэка; значение можно посмотреть в журнале отладки событий открытой платформы или сверить в карточке участника в адресной книге.
- «ID владельца» используется только для идентификации и не даёт прав на команды автоматически; всем пользователям DingTalk по-прежнему нужна веб-авторизация или добавление в список разрешённых.
- При создании по QR-коду `staffId` сканировавшего возвращается не всегда; его можно указать вручную. При первом использовании достаточно, чтобы учётная запись, которой принадлежит бот, вошла на веб-страницу и одобрила доступ.

### 3.4 Интеллектуальный бот WeCom (постоянное соединение)

В WeCom необходимо создать **интеллектуального бота** и выбрать **режим API → постоянное соединение**. Webhook группового бота WeCom умеет только отправлять сообщения и не принимает команды.

> Примечание об обновлении: устаревший колбэк собственного приложения WeCom (Token / EncodingAESKey / CorpID / AgentID) больше не используется для ботов команд. Существующих ботов нужно переключить в разделе «Боты команд» на Bot ID / Secret интеллектуального бота и сохранить настройки.

#### Добавление по QR-коду (рекомендуется)

1. На странице «Боты команд» нажмите **Добавить WeCom по QR-коду**.
2. Отсканируйте код в WeCom с учётной записью, имеющей право создавать интеллектуальных ботов, и, следуя подсказкам на странице, создайте и авторизуйте бота.
3. Система автоматически получит Bot ID / Secret, создаст бота и установит постоянное соединение; QR-код действителен 5 минут.
4. После создания попросите участника отправить команду — её должен одобрить владелец бота, войдя на веб-страницу; UserID владельца используется только для идентификации и не даёт прав автоматически.

> Если на той же платформе уже есть включённый бот или квота исчерпана, сканирование будет отклонено; сначала обработайте старого бота на странице.
>
> Для сканирования используется официальная страница авторизации WeCom. Если у учётной записи нет прав на создание интеллектуальных ботов или WeCom изменил процедуру на странице авторизации, можно воспользоваться ручной настройкой ниже.

#### Ручная настройка

1. Откройте [административную консоль WeCom](https://work.weixin.qq.com/) или рабочее пространство клиента WeCom и перейдите в «Интеллектуальные боты» → создать бота.
2. В процессе создания выберите «Создание в режиме API» → «Использовать постоянное соединение».
3. Получите и сохраните **Bot ID** и **Secret**. Secret обычно показывается только один раз; при утере его можно сгенерировать заново.
4. Создайте в системе «Интеллектуальный бот WeCom (постоянное соединение)», укажите Bot ID, Secret и UserID владельца.
5. Добавьте бота в групповой или личный чат; в групповом чате отправьте `/help` с **@бот**.
6. Указывать адрес колбэка, Token, EncodingAESKey или CorpID не нужно; сервис сам подключается к `wss://openws.work.weixin.qq.com`.

#### Поля на стороне системы

| Поле | Обязательно | Описание |
| ----------------- | -------- | ---------------------------------------------------------------------- |
| Название | Да | Только для идентификации в системе |
| Bot ID | Да | Уникальный идентификатор интеллектуального бота |
| Secret | Да | Secret только для постоянного соединения, используется для аутентификации `aibot_subscribe` |
| ID пользователя платформы-владельца | Желательно указать | UserID участника в адресной книге WeCom; ориентируйтесь на `from.userid` в фактическом колбэке бота |

#### Механизм постоянного соединения

- Сервер сам подключается к `wss://openws.work.weixin.qq.com`, что подходит для развёртывания во внутренней сети и не требует фиксированного публичного IP.
- После установки соединения отправляется `aibot_subscribe`, где Bot ID + Secret используются для аутентификации; далее каждые 30 секунд отправляется `ping`.
- Сообщения пользователей передаются в открытом виде через `aibot_msg_callback` и не требуют расшифровки; система обрабатывает только `msgtype = text`.
- Ответы отправляются через `aibot_respond_msg` с `req_id` из колбэка в формате markdown; ответы с одинаковым `req_id` отправляются последовательно.
- Для одного интеллектуального бота одновременно допускается только одно действующее постоянное соединение; новое соединение вытесняет старое, и при развёртывании нескольких экземпляров они будут прерывать друг друга.
- При разрыве соединения переподключение выполняется с экспоненциальной задержкой; при повторных ошибках аутентификации или замене соединения новым экземпляром на карточке бота отображается ошибка постоянного соединения.
- В сообщениях группового чата сначала удаляется префикс `@бот`, затем текст разбирается как слэш-команда.
- Отвечать можно в течение 24 часов после колбэка сообщения; команды выполняются в фоновой очереди, и длинные команды обычно занимают несколько секунд.
- После включения уведомлений о событиях система через то же постоянное соединение использует `aibot_send_msg` для активной отправки в последний сеанс; пользователь должен сначала отправить боту сообщение.

#### ID владельца и список разрешённых

- Указывайте **UserID** из адресной книги WeCom (учётная запись участника), а не имя, номер телефона или ID внешнего контакта.
- Если создатель бота не является супер-администратором организации, `from.userid` может быть зашифрованным userid в рамках организации; настраивайте владельца и список разрешённых по фактическому значению из события колбэка.

#### Неавторизованные пользователи и веб-авторизация

- Если пользователя WeCom нет в списке разрешённых, бот отвечает одноразовой ссылкой на веб-авторизацию (`PUBLIC_BASE_URL/authorize/<token>`), действительной 30 минут.
- Владелец бота входит на страницу по ссылке под своей учётной записью веб-интерфейса, проверяет ID пользователя платформы (а также доступные псевдоним и сеанс), выбирает `viewer` или `admin` и затем одобряет или отклоняет запрос.
- Пользователи, не являющиеся владельцем бота, после входа могут только просматривать запрос и не могут одобрить его самостоятельно; ссылку нужно переслать владельцу бота.
- Ссылка авторизации становится недействительной после однократной обработки; другие ожидающие ссылки того же пользователя обновляются автоматически. После истечения срока попросите пользователя отправить любую команду, чтобы получить новую ссылку.
- Всем участникам (включая самого сканировавшего) нужно получить права через веб-авторизацию или список разрешённых; если вы хотите получить полные права на команды, выберите при одобрении `admin`.
- `PUBLIC_BASE_URL` должен открываться из браузера; если ссылка не открывается, проверьте обратный прокси и эту переменную окружения.

#### Состояние соединения

На карточке бота отображается состояние постоянного соединения:

- **Установка соединения**: идёт подключение или автоматическое переподключение.
- **Соединение установлено**: аутентификация успешна, можно принимать команды.
- **Ошибка соединения**: неверные учётные данные, не указаны Bot ID / Secret, сеть недоступна, ошибка аутентификации или соединение заменено другим экземпляром.
- **Соединение не включено**: бот отключён.

Если ошибка сохраняется, проверьте Bot ID / Secret, разрешает ли исходящий трафик сервера подключение к `wss://openws.work.weixin.qq.com:443`, а также не использует ли тот же Bot ID другой экземпляр.

### 3.5 Уведомления о событиях от ботов

Если на странице редактирования бота команд установить флажок **Получать уведомления о событиях**, бот дополнительно будет получать события релизов, распродаж, снятия с продажи и т. п. Это отдельная от каналов уведомлений конфигурация, и обе можно включить одновременно.

- **Цель уведомлений**: сеанс, который последним использовал участник из списка разрешённых. Система обновляет эту цель только после успешной отправки команды авторизованным пользователем; действия неавторизованных пользователей её не меняют.
- **Предварительное условие**: бот должен был получить хотя бы одну команду от авторизованного пользователя, иначе доставка событий выполняться не будет. На карточке бота отображается «Последний сеанс ещё не записан».
- **Набор событий**: принимаются все события, включая ошибки проверки; фильтрация типов событий отдельно для бота не поддерживается.
- **Групповые боты в каналах уведомлений по-прежнему отправляют сообщения по собственным правилам выбора событий канала; эти механизмы не влияют друг на друга.**

Дополнительные требования по платформам:

- **Feishu / Lark**: требуются App ID / App Secret и право отправлять сообщения в сеанс от имени приложения. События отправляются в `chat_id` последнего сеанса; подходят оба режима — HTTP-колбэк и постоянное соединение.
- **DingTalk**: требуются App Key, App Secret, Robot Code и право бота активно отправлять сообщения. Для группового чата используется `openConversationId`, для личного — `staffId` отправителя.
- **WeCom**: через постоянное соединение `aibot_send_msg` доставляется в последний сеанс; для личного чата `chat_type=1`, для группового — `chat_type=2`. Пользователь должен уже иметь сеанс с ботом.

> Если бот отключён, уведомления о событиях выключены, последний сеанс удалён или бот исключён из группового чата, доставка отменяется или завершается ошибкой; чтобы обновить целевой сеанс, попросите авторизованного пользователя снова отправить команду.

## 4. Краткий справочник команд

```text
/help
/add <appid | ссылка на магазин | название> [--discount N] [--note текст] [--force]
/adddlc <appid базовой игры | ссылка | название> [--max 50]
/remove <id | appid | название>
/pause <id | appid | название>
/resume <id | appid | название>
/check <id | appid | название>
/price <id | appid | название>
/list [--all] [--sale] [--paused] [--page N]
/events [--item id] [--limit 10]
/cancel
```

Пояснения:

- `/add` поддерживает прямой поиск в магазине Steam; если поиск по названию возвращает несколько результатов, выберите нужный, ответив номером.
- `--discount N` задаёт порог уведомления о скидке (0–100); если не указан, используется значение учётной записи по умолчанию.
- `--force` используется, когда элемент недоступен в текущем регионе, но его всё же нужно добавить только для предупреждений по новостям.
- `/adddlc` импортирует все DLC базовой игры, не более 50 за один раз.
- `/check` обходит кэш, немедленно выполняет проверку и записывает события; на него влияют ограничения частоты Steam.
- `/list` по умолчанию не показывает приостановленные элементы; `--all` показывает все, `--sale` — только участвующие в распродаже, `--paused` — только приостановленные.
- `/events` по умолчанию показывает последние 10 событий, максимум 20.
- Роль `viewer` ограничена командами `/help`, `/list`, `/price`, `/events`.

## 5. Устранение типичных проблем

| Симптом | Возможная причина | Действия |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Не удаётся сохранить адрес колбэка Feishu / Lark / DingTalk | Сервис недоступен из интернета, сертификат недействителен, неверный `PUBLIC_BASE_URL` | Откройте домен колбэка с мобильного интернета; убедитесь в полноте цепочки HTTPS-сертификатов; проверьте, что бот создан и включён |
| Колбэк Feishu / Lark / DingTalk возвращает 404 | Бот отключён или удалён, либо неверно указан `<slug>` | Скопируйте актуальный адрес колбэка на странице «Боты команд»; включите бота |
| Feishu / Lark сообщает об ошибке проверки / 401 | Несовпадение Verification Token или Encrypt Key; прокси изменил тело запроса | Сверьте значения с обеих сторон; отключите сжатие / перезапись тела запроса; сохраняйте заголовки `X-Lark-*` |
| Feishu / Lark: после включения шифрования бот не отвечает | На платформе включён Encrypt Key, но в системе он не указан, поэтому шифротекст не удаётся разобрать; также возможен прямой ответ 401 из-за проверки Verification Token | Укажите в системе те же Encrypt Key и Verification Token либо отключите шифрование на платформе и сохраните настройки заново |
| Feishu / Lark получает сообщения, но не может ответить | Не указаны App ID / App Secret или отсутствует право на отправку сообщений | Дополните учётные данные; запросите и опубликуйте право на отправку сообщений в открытой платформе |
| Соединение Feishu / Lark долго остаётся в состоянии «подключение» или ошибки | Неверные App ID / App Secret; в приложении не включено «Получать события через постоянное соединение»; организация ограничивает создание по QR-коду | Сверьте учётные данные; переключите события и колбэки на постоянное соединение и опубликуйте версию; либо перейдите на HTTP-колбэк |
| После сканирования бот Feishu / Lark не находится | Приложение не опубликовано или область доступности не включает этого участника | Создайте версию и опубликуйте приложение в открытой платформе, скорректируйте область доступности; ищите по названию приложения |
| После сканирования QR-кода Feishu создано приложение Lark | Учётная запись, сканировавшая код, относится к тенанту Lark, и система автоматически сменила домен авторизации | Это нормальное поведение; найдите приложение по названию в Lark |
| Колбэк DingTalk возвращает 401 | Неверный App Secret; прокси удалил заголовки; отклонение времени сервера превышает 1 час | Сверьте App Secret приложения (не секрет подписи); сохраняйте `timestamp`, `sign`; синхронизируйте время по NTP |
| Тайм-аут / ошибка ответа DingTalk | Срок действия `sessionWebhook` истёк | Отправьте команду повторно; убедитесь, что колбэк завершается за несколько секунд |
| DingTalk Stream не подключается / ошибка | Неверные Client ID / Secret; для бота не выбран режим Stream; приложение не опубликовано; сервер не может исходящим соединением обратиться к `api.dingtalk.com` | Сверьте учётные данные; выберите Stream в настройках бота и опубликуйте версию; проверьте исходящую сеть |
| DingTalk сообщает об ошибке авторизации при сканировании | У учётной записи нет прав разработчика; QR-код истёк; выбранная организация не разрешает создание приложений; не удалось загрузить шаблон страницы авторизации | Убедитесь, что у учётной записи есть права разработчика в целевой организации; сгенерируйте QR-код заново; выберите организацию с нужными правами; если ошибка сохраняется, посмотрите в логах сервиса причину «ошибка авторизации DingTalk по QR-коду» |
| После сканирования бот DingTalk не отвечает | Приложение не опубликовано или область доступности не включает участника; бот не добавлен в сеанс; соединение Stream не установлено | Опубликуйте приложение и скорректируйте область доступности; проверьте состояние соединения на карточке бота; отправьте команду повторно |
| Пользователю DingTalk / Feishu сообщается об отсутствии авторизации | Пользователь платформы отсутствует в списке разрешённых и не прошёл веб-авторизацию | Попросите пользователя отправить любую команду, чтобы получить ссылку авторизации, и одобрите её, войдя на веб-страницу под учётной записью владельца бота, либо сразу добавьте пользователя в список разрешённых |
| Постоянное соединение WeCom не установлено / ошибка | Неверные Bot ID или Secret; сервер не может исходящим соединением обратиться к `openws.work.weixin.qq.com:443`; другой экземпляр использует того же бота; бот отключён | Сверьте Bot ID / Secret; проверьте исходящий firewall и прокси; убедитесь, что нет дублирующего развёртывания; посмотрите состояние и текст ошибки на карточке бота |
| WeCom: на сообщения нет ответа | Постоянное соединение разорвано; сообщение пришло за пределами 24-часового окна ответа; во время обработки бот был отключён или удалён | Проверьте состояние постоянного соединения; отправьте команду повторно; убедитесь, что бот остаётся включённым |
| WeCom сообщает, что соединение заменено | Для того же Bot ID установлено новое соединение, и WeCom отключил старое | Оставьте для каждого бота только один работающий экземпляр; остановите дублирующие развёртывания либо отключите и снова включите бота в системе |
| Команды не отвечают | В групповом чате не указан @бот; сообщение не является текстовым; не начинается с `/`; пользователь отсутствует в списке разрешённых | Укажите @бот в группе; отправьте `/help`; добавьте ID пользователя платформы в список разрешённых |
| У самого сканировавшего тоже нет прав на команды | ID владельца используется только для идентификации и больше не даёт прав неявно | Одобрите свою учётную запись платформы на странице веб-авторизации либо попросите владельца бота добавить ваш ID платформы в список разрешённых |
| Конфликт при создании бота | На той же платформе уже есть включённый бот | Сначала отключите старого бота, затем включите нового |
| Тест канала уведомлений не проходит | Webhook недействителен, неверный ключ подписи, ограничения по ключевым словам / белому списку IP | Скопируйте Webhook заново; сверьте ключ подписи; проверьте настройки безопасности платформы |
| В группу не приходят уведомления о событиях | Канал отключён, типы событий не отмечены, групповой бот удалён | Проверьте состояние канала и подписку на события; отправьте тестовое сообщение повторно |
| Бот не отправляет уведомления о событиях | Не включено «Получать уведомления о событиях»; нет последнего авторизованного сеанса; в DingTalk отсутствуют App Key / Robot Code; бот отключён | Включите уведомления в настройках бота; попросите авторизованного пользователя сначала отправить команду; дополните учётные данные DingTalk; проверьте записи доставки |
| Feishu / Lark / DingTalk повторно присылает одно и то же сообщение | Платформа не получила ACK вовремя или произошёл сетевой сбой | Система выполняет дедупликацию по ID сообщения; обеспечьте возврат колбэка в течение 10 секунд |

### Рекомендации по отладке

1. Сначала воспользуйтесь кнопкой **Имитация команды** на карточке «Боты команд», чтобы локально выполнить команду от имени владельца бота и убедиться, что логика команд и квоты работают.
2. Затем проверьте Webhook и подпись с помощью **Отправить тест** в «Каналах уведомлений».
3. Наконец, отправьте `/help` в чате платформы, чтобы проверить колбэк / постоянное соединение, права и цепочку ответов.
4. Просматривайте логи контейнера: `docker compose logs -f steam-monitor`, обращая внимание на записи, связанные с `wecom`, `webhook`, `inbound`, `delivery`.

## 6. Рекомендации по безопасности

- Адреса колбэков Feishu / Lark / DingTalk, Webhook групповых ботов и Bot ID / Secret WeCom считаются учётными данными: не публикуйте их в открытых репозиториях и не отправляйте в публичные группы.
- Для HTTP-колбэков Feishu / Lark рекомендуется включить Encrypt Key + Verification Token; учётные данные постоянного соединения также нужно хранить в тайне. Для HTTP-колбэка DingTalk App Secret необходимо указывать для проверки подписи, а в режиме Stream также защищать Client Secret; в WeCom необходимо защищать Bot ID и Secret постоянного соединения.
- Придерживайтесь принципа минимальных привилегий в списке разрешённых: обычным участникам назначайте `viewer`, `admin` — только администраторам.
- Не выставляйте файл SQLite в интернет; регулярно создавайте резервные копии базы данных и одновременно сохраняйте копию `APP_SECRET` из `.env`.
- После изменения `PUBLIC_BASE_URL` или смены домена своевременно обновите адреса колбэков в консолях Feishu / Lark / DingTalk; режим постоянного соединения это не затрагивает.
- При подозрении на утечку учётных данных: в Feishu / Lark сбросьте App Secret / Encrypt Key, в DingTalk — Client Secret, в WeCom заново сгенерируйте Secret интеллектуального бота и укажите новые значения в системе.
